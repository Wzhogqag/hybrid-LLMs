00 / 先读核心结论

① 策略层成果明确

Marconi 解决的是 Hybrid KV + SSM 的准入和 FLOPs-aware 驱逐；其 Fig. 7/8 可以由公开 trace-driven artifact 复现。

② 不是可见的 SGLang fork

思想与 SGLang RadixCache 接近，但开源实验入口直接使用独立 Python RadixCache / RadixCacheVLLM 模拟类。

③ 物理地址不可验证

论文描述 KV 与 SSM 状态如何归属与淘汰，却没有公开完整的 GPU block table、state slot allocator 和两者映射代码。

对“端到端”的审慎解释论文 §5.2 标为 End-to-End Results，并报告使用 vLLM 在四张 A100 上测量 Jamba-1.5-Mini。然而，公开的 Fig. 9 绘图程序按 input_tokens - cached_tokens 查找预先采样的 TTFT 曲线，属于模型性能画像 + 缓存 trace 回放的估算链；它不能独立证明三套完整 Hybrid Prefix Cache 推理服务均已实现和实测。参见 ttft.py L14–20、L160–188。

术语纠正：vLLM 当时“不支持”的究竟是什么？论文说当时 vLLM / SGLang 不原生支持 Hybrid/SSM 模型的 Prefix Caching，而不是 vLLM 根本无法加载或推理 SSM 模型。否则就无法在 vLLM 中进行 Jamba 性能测量。支持模型执行 ≠ 支持跨请求复用其 recurrent states。

公开代码如何选择基线？

# policy_exploration.py 的核心抽象（便于理解的提炼示意）
radix_tree_class = {
    "selective": RadixCache,        # Hybrid, strategies V1/V2/V3
    "all": RadixCacheVLLM,         # fixed-block baseline
}[admission_strategy]

# 实验入口不是 engine.generate()，而是：
for request in all_requests:
    radix_tree.match_prefix(request["input_tokens"])
    radix_tree.insert(
        token_ids=request["input_tokens"] + request["output_tokens"],
        state_at_leaf=request["session_id"],
        state_at_branchoff=request["session_id"],
    )

证据含义：session_id充当模拟器状态标记，不是 GPU 上真实 KV/SSM tensor 的地址。源码所在：policy_exploration.py、radix_cache_vllm.py、radix_cache_hybrid.py。

vLLM+“改了什么”：哪些是语义，哪些有 GPU 证据？

  • 论文定义：把常规 block prefix cache 扩展为可缓存 SSM 状态，选用 32-token block 的细粒度 checkpoint。
  • 公开模拟器：实现固定 block 对齐的插入、命中和 LRU 式驱逐成本模型。
  • 缺失：公开 artifact 没有给出匹配 vLLM 版本的完整 scheduler / block manager / SSM CUDA storage 补丁，也没有展示每个 32-token boundary 的真实 GPU state snapshot 拷贝逻辑。
更精确的判断Marconi 从 Radix Tree 管理思想上接近 SGLang；它在论文中同时构造 vLLM+、SGLang+ 作为扩展基线；但当前仓库不能证明作者把实际 Marconi 代码建立在某个特定 SGLang commit 的后端上。

04 / Fig. 9 TTFT 结果具体如何得到？

这里存在三个容易被论文标题混在一起的层次。我们从公开 plotting/ttft.py 逆向梳理。

阶段 A：真实性能画像

用 Jamba-1.5-Mini 收集不同 Prefill 长度的 TTFT 数据，保存到 ttft_AI21-Jamba-1.5-Mini.pickle。

阶段 B：策略模拟

V1、V2、vLLM+ 对相同 token trace 回放，得到 (hit?, input_length, cached_length)。

阶段 C：延迟估算

对缓存方案调用 TTFT(input_length - cached_length)；对 Vanilla 调用 TTFT(input_length)。

# plotting/ttft.py 原函数的关键两行
# x[1] = input token length; x[2] = hit prefix length
ttft_original = [get_approximate_ttft(x[1]) for x in request_history]
ttft_scheme   = [get_approximate_ttft(x[1] - x[2]) for x in request_history]

# 然后在每份 trace 上统计 P95
return np.percentile(ttft_original, 95), np.percentile(ttft_scheme, 95)

程序还对原始 pickle 的 TTFT 曲线使用线性回归平滑，get_approximate_ttft() 的注释注明了早期 profiling 秒到毫秒换算的问题。真实模型 profiling 确实存在；但缓存收益并未由三个修改版完整 GPU 推理服务逐请求直接测得。

能证明 / 不能证明能：在某条实际测量的长度—延迟曲线假设下，模拟复用不同 token 数量预计带来怎样的 P95 改善。
不能：真实 checkpoint 额外 Prefill、state pool 分配、GPU kernel 状态搬移、跨请求同步、碎片及前缀恢复时序的完整开销。因此“论文报告了 TTFT”不应被误读为“公共仓库提供了完整 Hybrid 推理系统实现”。

05 / 逻辑层：一个 Radix Tree，KV 与 SSM 怎样对应？

Marconi 用同一 token 前缀路径作为 KV 与 SSM 的逻辑身份：同一个节点描述某个精确 token 区间与其结束处的 checkpoint。它并不要求所有组件都有同样的保存粒度——KV 可表示 token 片段，而 SSM 是边界处的固定大小整体状态，选择性准入使中间节点不一定保存 SSM。

Root
↓
Prefix P = [1,2,3,4]
↓ state handles
KV：token [1..4] 的状态片段
SSM：prefix P 末尾的 state snapshot（若已准入）

这是逻辑归属示意，并不表示两个状态存放在同一 HBM 连续区域。

为什么两个状态的复用规则不同？

Attention KV：可以按前缀分割、保留和重组，因此某个节点不持有 SSM state 时，其 KV 仍可能有意义。

SSM：recurrent state 随 token 原地更新；持有 position 528 的 state 不等于拥有 position 512 的 state，不能随意回滚。

因此，真正跳过 Hybrid Prefill 必须找到所有必要状态均可在某个共同边界合法恢复的位置。

SSM 在哪些位置准入？

  1. Input + Output 前缀：每个生成序列最后的 state 容易成为下一轮对话的恢复点，因此保存末端 checkpoint。
  2. Purely-input shared prefix：执行 Prefill 之前先在树里 speculative insertion，若会形成新的分叉节点，才请求在该前缀边界保存 SSM state。
  3. 结果：论文称每个序列最多承认约两处 SSM state 的准入，避免在每个细小 block 都保存巨大 checkpoint。
精确性边界：chunk state vs two-pass prefill论文 §4.1 讲：若目标是 token 80 但模型使用 32-token chunks，可以在 token 64 物化 state，这是合法但更短的可复用前缀，不是将 64 伪装成 80。对于不能 chunk-passing 的模型，可以两遍 Prefill：第一遍到 80 保存精确 state，第二遍继续计算剩余 20；这才得到精确 80 的状态。论文没有公开真实 GPU 双遍 Prefill 的额外耗时基准。论文 §4.1 / PDF 第 5–6 页。

06 / 物理内存与地址：论文究竟写到了哪一步？

6.1 状态成本公式 ≠ 物理分配器

Appendix A.1 把 FP16 下的状态内存建模为：

Attention 单层 KV bytes = 2 × L × D × 2 = 4LD
SSM 单层 main state bytes = D × N × 2 = 2DN
SSM Conv1D state bytes = in_channels × conv_kernel × 2

L = 前缀 token 数；D = hidden/model dimension；N = recurrent state dimension

KV 占用随 L 增长；SSM 单个 checkpoint 的大小与 L 无关。论文 Table 1 为方便解释省略 Conv1D，在实际实验的状态成本统计里计入，7B 模型中约占状态的 6.1%。这些是 capacity accounting 的依据，不是 CUDAMalloc / BlockManager 的实现证据。Appendix A.1 / PDF 第 15 页。

6.2 驱逐中间节点：逻辑所有权变化

驱逐前

Node A [1,2]
KV_A + SSM_A
↓ 唯一子节点
Node B [3,4]
KV_B + SSM_B

驱逐后

Merged Node B [1,2,3,4]
KV_A + KV_B; SSM_B
↓

释放 SSM_A；吸收 KV_A 到 B 的逻辑范围。

“吸收”可能通过引用改挂而不是物理搬运实现，但论文和公开源码不能确认采用哪种方式。

论文 §4.3 明确允许淘汰子节点数 ≤1 的中间节点（而非只淘汰叶子），以及 “intermediate node 被驱逐时 SSM states 被释放、KVs 被 child 吸收”；同时只更新实际访问节点的时间戳，不必刷新所有祖先。这说明了逻辑管理语义，却没有给出物理 KV block 重绑、释放与压缩的 CUDA 数据结构。§4.3 / PDF 第 7 页。

6.3 “逻辑地址”应该分成 4 种含义

层次含义Marconi 公开证据状态
前缀身份Token 序列、Radix Tree 路径、分叉节点TreeNode.value、parent/children、get_all_token_ids()明确
缓存对象身份KV 区间与 SSM checkpoint 归属于哪个前缀HybridStates.kv_cache / mamba_states 的结构抽象结构明确
逻辑 page / slot IDKV block table ID；SSM state slot ID；两类型如何对齐或独立编号没有完整的公开映射表或 allocator 代码不可确认
GPU HBM 地址物理 tensor、地址偏移、内存池、释放和搬移Python 策略模拟类不执行真实 GPU 申请不可确认
严禁混淆 logical_ts 与逻辑地址公开实现中的 logical_ts 是访问/驱逐相关的逻辑时间戳，不是逻辑 page number，也不是 KV/SSM slot id。不能由“统一 Radix Tree”推导出“统一页号”“统一物理页大小”或“同一个 allocator”。

6.4 一个合理的工程实现假说——但不是源码事实

                  Unified Token-Prefix Radix Tree
                              |
                         Prefix Node P
                       /              \
               KV handle(s)         SSM checkpoint handle
                    |                         |
             KV block table             SSM slot table
                    |                         |

08 / 证据分级：不把推断当事实

断言等级依据 / 注意
Marconi 使用统一 token-prefix Radix Tree 管理 KV/SSM 的逻辑身份论文 + 逻辑源码支持§4.1、RadixCache / HybridStates
SGLang+ = Marconi 的 admission + LRU；Marconi 引入 FLOPs-aware eviction直接支持§5.1、artifact V1/V2
vLLM+ 每 32-token block 密集存 SSM checkpoint论文直接支持§5.1；公开模拟器实现该语义
主策略评估是 trace-driven、state marker 并非 GPU tensor源码直接支持policy_exploration.py
Fig. 9 用缓存长度映射 Jamba measured-profile 估算 TTFT源码直接支持plotting/ttft.py
Marconi 的原型直接修改了 SGLang 的某个完整引擎版本未证实公开仓库无对应完整 fork / commit / 服务启动脚本
KV 采用可分页内存组织，SSM checkpoint 为固定大小状态设计原则明确论文背景、§4、Appendix A.1；具体物理方案未公开
作者实际采用独立 KV block pool 和 SSM state pool合理猜想，不可确证缺完整 allocator
KV 和 SSM 共用逻辑页号、共享一套物理页大小没有证据统一前缀索引不意味着统一页表/页号
GPU KV 通过重新引用无拷贝吸收到子节点设计推测论文只承诺逻辑“absorb”，没有证实实现方式

09 / 对 Hybrid Prefix Management 研究的意义

Marconi 已经回答的问题

  • 哪些共享前缀值得保存 SSM checkpoint？（针对输入分叉 / 对话末尾选择性准入）
  • 哪些缓存项应该被驱逐？（recency 与 FLOPs saved/byte 的权衡）
  • 统一前缀树里如何处理不同类型状态的复用语义和中间节点删除？（逻辑层管理）

Marconi 尚未通过公开代码明确证明的问题

  1. 物理布局：KV pages、SSM slots、Conv1D state 是否独立分配？哪个地方保存 cross-type handle？
  2. 逻辑粒度：各层各类 state 的 checkpoint boundary 是否必须统一，或可存在独立有效范围？
  3. 精确恢复：只有部分状态命中时，如何精确重算其余状态而不丢掉已命中的 KV 收益？
  4. 运行时成本：两遍 Prefill、checkpoint 复制、内存碎片、GPU 同步及 allocator 争用带来多少真实 TTFT？
与你的 Qwen3.5-9B 实验的直接连接你观察到的 Mooncake 512-token 共享粒度与 vLLM align 的 528-token joint cache geometry 错位，是能够在真实引擎中复现实测的状态边界与分配粒度问题。它比从 Marconi 逻辑树代码猜 GPU 页表更适合作为下一步系统问题的实证入口。独立实验页面：Qwen3.5-9B Hybrid Prefix Geometry。

下一步优先验证的四个问题

  1. 在最新 vLLM 中，KVCacheSpec / MambaSpec 与 block pool 的索引如何关联？是否所有层类型共享 block index？
  2. 一个不对齐的 512-token 精确共享前缀，哪些 Attention KV 在内部实际上可命中、却因为 GDN checkpoint 不可用而整体无法复用？
  3. 做一个两种状态独立驻留的最小原型，是否能实现精确恢复并缩短 TTFT？额外重算成本与 HBM 节省如何量化？
  4. 改变 batch、state dtype、TP、backend 后，528 的 block geometry 如何变化？结果是否稳定？
