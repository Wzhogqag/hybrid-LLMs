00 / HOW TO READ

先约定：哪些是结论，哪些只是例子

Jenga 把“某一类型缓存的复用单元”与“跨类型重新分配容量的单元”分成了两层。

子页承载一组兼容层的 KV 或状态；LCM 大页决定哪些容量能整体回到共享池。前缀复用仍需满足所有类型共同的恢复条件，跨类型调整容量仍受大页可回收性的约束。

标识本文怎样使用
源码结论可以在固定提交的函数、字段或控制流中找到依据。
教学例子人为选择数字或简化模型帮助理解；不会冒充论文配置或程序实际输出。
边界 / 假设需要进一步实验或执行路径审计，不能当成已证实的新问题。

论文依据为作者的 arXiv v1；实现依据为作者公开的原型，而不是任意版本的上游 vLLM。论文设计与原型细节分别说明；下文的 level0 指大页，level1 指子页。

保留这条版本边界

作者仓库说明上游 vLLM 有简化、较稳定的版本。它不能推出“现在的上游已经完整采用这里的 LCM 分配器和全部驱逐路径”。本笔记也不把原型实现直接称为当前 vLLM 实现。

01 / OBJECTS

这里的“页”，不是一个统一的概念

对象它表示什么谁负责
请求的逻辑 token block例如第 32–47 个 token（从 0 开始），在某个缓存组中的逻辑位置。请求的 block table 与类型管理器
Jenga 子页 / level1 page某个组的一份实际缓存存储单元；FA / SWA 通常对应一个 token block，递归状态对应一个边界状态。类型分配器与前缀缓存分配器
Jenga LCM 大页 / level0 page共享 GPU buffer 内的一段软件管理区域，可切成同一类型的若干子页。全局大页池与两级驱逐器
GPU 虚拟内存页GPU 地址空间到实际显存的映射粒度；不是由上述子页 ID 直接定义。CUDA 驱动 / GPU MMU

它继承了 PagedAttention 的“逻辑 token block 经 block table 找存储块”的思路，但 LCM 大页是 Jenga 在缓存分配器内增加的层次。这里的 page 不能直接等同于操作系统物理页或某个固定的 2 MB CUDA 页。

先记住一句话

子页有实际的 GPU buffer 字节作为后盾，但“子页 ID”是软件索引；从这个 ID 算出的指针是 GPU 虚拟地址。

依据：_compile_two_levelCacheEngineV3._allocate_kv_cacheCUDA 地址映射说明

检查点：如果说“驱逐一张大页”，首先理解为把 Jenga 缓存池内的一段容量改作他用，而不是驱动卸载一张显存物理页。

02 / GROUPING

一张子页，到底包含多少层？

在这里审计的两级分配路径中：包含同一个兼容组的全部层，不是固定一层，也不是固定六层。

源码结论 编译配置时先按单层页大小与 get_app_property() 分组，再让同组层共享一套 block table。组内单层页大小一致，组子页大小为单层页大小乘以组内层数。

ng = 组 g 中兼容层 / 组件的数量
sg = 组内单层的一页大小
Sg = ng × sg = 一张组子页大小

兼容性不是只看“FA、SWA、Mamba”三个名称。原型的应用属性还编码页大小、滑窗大小或状态大小等信息。不同滑窗、不同大小的状态可能落入不同组。

组的例子一张组子页存什么不应怎样理解
6 个兼容的 FA 层同一个 token block 在这 6 层中的 KV。不是整个模型全部层；也不是只存一个 token。
4 个兼容的 SWA 层同一个 token block 在这 4 层中的 KV；窗口语义由管理器处理。子页本身不是完整滑动窗口。
若干兼容的递归状态组件某个恢复边界上，这些组件各自的一份状态。若 checkpoint 间隔为 512，不代表存 512 份状态。

对一个 Mamba 层，卷积状态和 SSM 状态可以注册为不同的管理组件。因此文中的“层”在源码语境下有时更准确地应叫“缓存组件”；不能默认一张 Mamba 子页只对应一个完整模块。

展开：直接去哪些函数核对

_compile_get_kv_cache_config() 收集组；_compile_two_level() 用组大小计算子页，并将每个层的起点设置为它在组内的序号乘以单层页大小。此路径没有“固定每两层一组”的规定。

不同 dtype 不是随意混放：这一配置编译入口要求管理器使用同一 dtype；源码的大小通常以元素数计，本文说明布局时转换为字节。

依据：_compile_two_level分组入口各类型应用属性Jamba 状态注册

检查点：“一张子页存所有层的一个 token”不准确。对 FA，应说“同组全部层的一个 token block 的 KV”。

03 / TWO LEVELS

LCM 大页与子页，能怎样解耦？

教学例子 假设类型 A 有 2 个兼容层，每层一页 128 B；类型 B 有 3 个兼容层，每层一页也为 128 B。这些数字只用于演示整除关系。

类型一张子页一张 LCM 大页可以放
A2 × 128 = 256 B768 / 256 = 3 张 A 子页
B3 × 128 = 384 B768 / 384 = 2 张 B 子页
L = lcm(SA, SB, …) = lcm(256, 384) = 768 B
rg = L / Sg
子页 ID = 大页 ID × rg + 页内子页序号

大页分给 A 后

第 0–255 B 是 A 子页 0；第 256–511 B 是 A 子页 1；第 512–767 B 是 A 子页 2。

一个 256 B 空位不能直接供 B 的 384 B 子页使用。

整张大页回收后

同一段 768 B 可以改分给 B，变成两个 384 B 子页。

改变的是软件解释与分配元数据，不需要为此搬移整个缓存池。

源码结论 一张已归属某组的大页按该组子页大小切分。不同类型共享全局大页池，但没有在这条路径中任意混装不同大小子页。

解耦是有范围的

子页可独立命中、引用和驱逐；跨类型容量回收仍依赖整张大页。它提供“类型内的小粒度管理 + 类型间的大粒度转换”，不能直接理解为每个子页都能独立返回一个通用字节池。

子页 ID 必须带上类型语境。例如大页 5 对 A 的子页 ID 为 15、16、17；对 B 为 10、11。这不意味着同一时刻该大页同时属于两种类型。单独一个整数 ID 不是全局唯一的物理地址。

展开：LCM 解决什么，没有解决什么

它保证每个类型的组子页都能整除大页，避免在已定型大页内按固定最大块填充。但它不自动消除 token block 尾部未填满、暂时无法归还的大页、保留的冷缓存或配置预留空间。

原型还为避免带偏移 view 越界保留了一个大页的余量。因此不能仅凭“使用 LCM”宣称所有 GPU 内存浪费为零。LCM 数值对尺寸组合的敏感性，也需要针对模型配置实测。

依据：LCM 与组页大小small / large ID 换算与归还两级分配设计

04 / ADDRESS SPACES

逻辑地址、GPU 虚拟地址和物理地址

1请求与组：(request, group, token_block_index)
例如请求 R 的 FA 组中第 2 个 token block。
2block table 给出软件子页 ID
代码有时把它称为 physical block ID；此处 physical 指实际存储槽位，而非 GPU MMU 物理页。
3buffer 基址 + 子页偏移 + 层偏移 + 元素偏移
得到 kernel 使用的 GPU 虚拟地址。
4CUDA 驱动与 GPU MMU 完成地址翻译
实际显存物理位置属于更低一层；Jenga 的子页表不承担这一步。

权重地址和缓存地址隔离吗？

通常是同一 GPU 虚拟地址空间中互不重叠的分配区域。权重有自己的 tensor 与地址范围，Jenga 的缓存有自己的 buffer；这不是为缓存额外建立了一个独立 MMU 地址空间。大页在缓存类型之间重新分配，不会因此去重新排列模型权重。

如果之前按 2 MB 排布物理页呢？

你实际做的事与 Jenga 的关系
把一块 GPU buffer 按 2 MB 软件切分仍是软件分配层；与 Jenga 大页粒度的选取直接相关，但“2 MB”不证明它是 MMU 页。
通过 cuMemCreate / cuMemMap 控制分配与映射涉及 CUDA VMM 层，需进一步协调映射粒度、地址连续性、对齐与映射更新。

CUDA 可用粒度应从对应设备与 API 查询，不能一律写死为 2 MB。本文审计的 Jenga 路径分配一个 GPU tensor buffer，再建立 view；没有据此证明它逐子页执行 CUDA VMM 重映射。

依据：buffer 分配与 viewNVIDIA VMM 说明cuMemGetAllocationGranularity 等 API

05 / BYTE LAYOUT

多个 token：层挨着层，还是 token 挨着 token？

在下面这个 FlashAttention 路径中，外层先按组内的层排布；单层内部先 K、后 V，K / V 各自再排 token。

教学配置 组内 2 个 FA 层，block 大小 B = 16，KV heads = 1，head dimension = 64，BF16 = 2 B。该配置是便于算地址的完整例子；不同 backend 的内部维度顺序可能不同。

每层 K 或 V：P = 16 × 1 × 64 × 2 = 2,048 B
单层完整 KV 页：s = 2P = 4,096 B
组子页：S = 2s = 8,192 B
0–2,047 B层 0 · K：token 0 到 15 的所有 KV head / dimension
2,048–4,095 B层 0 · V：token 0 到 15 的所有 KV head / dimension
4,096–6,143 B层 1 · K：token 0 到 15 的所有 KV head / dimension
6,144–8,191 B层 1 · V：token 0 到 15 的所有 KV head / dimension

图中的 token 0–15 指页内偏移。不是先放层 0 的 token 0、再放层 1 的 token 0、再放所有层的 token 1。对这个 FlashAttention backend，K / V 内部布局为 [token, kv_head, dim]。

从逻辑 token 算到 GPU 地址

设 t 是从 0 开始的逻辑 token 序号，j 是组内层序号，q 是 block table 中的子页 ID，c=0 表示 K、c=1 表示 V。

# 为说明字节布局写的等价伪代码，不是原文件逐字摘录
b = t // B
r = t % B
q = block_table[request][group][b]
address = buffer_base + q*S + j*s + c*P
          + ((r*Hkv + head)*D + dim)*bytes_per_element
可操作的地址计算

改一个索引，看字节偏移怎样变化

固定 B = 16、两层、BF16、Hkv = 1、D = 64；示例 block table = [2, 5, 7, 1]。展示的是相对 buffer_base 的字节偏移，不是真实显存地址。

逻辑 block 2 → 子页 7；页内 token = 3
buffer_base + 61,834 B
57,344 + 4,096 + 0 + 394 = 61,834

默认例子：t = 35，因此逻辑 block 为 2、页内偏移为 3；表中第 2 项为 q = 7。取层 1 的 K、head 0、dim 5，偏移为 61,834 B；改为同一位置的 V，则为 63,882 B。

展开：源码怎样让这个布局真正落到 kernel 上

配置给每层设置组内起点 start_bias；CacheEngineV3 在同一个 buffer 上建立 K 与 V 的 view。这里 FlashAttention 的单个 K/V view 以半页为步长。

原型并不是把裸子页 ID 原封不动交给这个 view：Block 的执行用 ID 先乘以组内层数 n，FlashAttention 准备 block table 时再乘 2。因而 K 的执行块号为 2 × n × q。

本例为 2 × 2 × 7 = 28；乘以 K 半页 stride 2,048 B，得到组子页基址 57,344 B，再加层 view 起点与页内元素偏移。两次 ID 变换与统一字节公式一致。

这解释的是固定原型中的指定 backend 路径。不要把该 K/V 内部排列套给所有 xFormers、量化 KV 或其他版本内核。

依据：层起点K / V view执行块号乘数Flash 布局Flash 的 ×2 变换

检查点：“逻辑地址怎么确定”的第一步是 token 位置除以 B；“存在哪里”的第一步是查该组的 block table。不能直接把逻辑 block 序号当作存储子页号。

06 / LIFETIME

先分清三种子页，再看代码术语

判断一张子页能不能给新请求，先问两件事：现在有没有请求在用？如果没有，里面的旧前缀还要不要保留？

前文曾用 F、C、A 作为示意缩写。它们只是本笔记的标记，不是 Jenga 规定的三种页类型。这里改成完整中文名称，后文也统一使用中文。

子页状态现在是什么情况新请求能直接覆盖吗？
正在使用
旧标记 A：Active		至少有一个请求正在引用其中的 KV 或状态。引用计数 refcount > 0，就是“还有使用者”。不能直接覆盖，也不能作为普通驱逐对象。相同前缀的请求可以共享它。
保留旧前缀，暂无请求使用
旧标记 C：Cached		使用者数量降到 0，但已计算的旧 KV / 状态仍有复用价值，前缀查找表也仍然指向它。要存不同内容，必须先驱逐旧缓存；相同前缀命中则直接重新使用。
可直接分配的空位
旧标记 F：Free		没有请求占用，也没有需要保留的有效前缀绑定。显存中可能残留旧字节，但系统已不再把它们当作可复用缓存。可以，不用先牺牲一个有效前缀。这里的“空”是分配状态，不表示字节全部为 0。

请求结束后，子页会怎样？

  1. 如果还有别的请求共享它，仍然是正在使用。
  2. 如果已经没有使用者，但保留着可复用的已计算前缀，就成为保留旧前缀，暂无请求使用的子页。
  3. 如果不保留有效前缀，释放后就成为可直接分配的空位。

所以“没有请求使用”并不等于“可以不经驱逐直接覆盖”。这正是第二种与第三种状态的区别。

hashless：这里究竟在找什么？

hash 在这里是前缀内容的指纹，用来查“这份前缀已经存在哪张子页”。hashless 字面意思是“尚未绑定这种内容哈希”。

在后面的分配流程里，“向 hashless allocator 申请一张子页”可以先读成：找一个可以直接分配、无需先驱逐旧前缀的槽位。这个分配器也跟踪它已经发给请求的块，因此不能反过来说“凡是归它管理的块，都处于空闲状态”。

和“从旧缓存里腾位置”分开理解

找可直接分配的空位，不会丢失一个有效前缀；从保留旧前缀的子页中腾位置，则需要驱逐。保存这些可驱逐缓存候选的管理结构，在源码中叫 evictor。

“亲和限制”：只是空位优先给哪个请求

具体例子 请求甲触发分配了一张大页，里面有 3 个子页槽位。甲先用了第 1 个，余下两个空位会被记为“优先给甲”。甲继续申请时，分配器尽量从这里拿空位。

源码把这种尽量将同一请求的子页放在一起的偏好叫“请求亲和”。它不表示两个请求的 token 相似，也不表示这两个空位已经被甲实际占用。

源码词用中文怎么读是否已经有人占用？
当前请求的优先空位目前没人用，但先安排给当前请求。没有。
no_prefer目前没人用，也没有指定优先请求。没有。
affine_only=True这轮先不拿“优先给其他请求”的空位；仍可用自己的优先空位、无优先对象的空位，或按条件申请新大页。限制的是空位选择范围。
affine_only=False这轮也允许拿“优先给其他请求”的空位。仍然只能拿空位，不能覆盖其他请求正在使用的子页。

为什么这样安排？如果一个请求的子页尽量集中在几张大页里，它释放这些子页后，就更有机会让整张大页一起空出来。这里的优先关系可以被后续分配打破，不是独占所有权。

把整张大页的变化写完整

下面只演示“不保留旧前缀、实际释放成空位”的路径。请求甲和请求乙需要同一个缓存组的子页。

事件第 1 张子页第 2 张子页第 3 张子页结果
甲取得大页，用一张子页甲正在使用空位，优先给甲空位，优先给甲两个空位尚未被甲占用。
乙在允许借空位的阶段拿走一张甲正在使用乙正在使用空位不同请求可以使用同一大页。

展开：请求移除以后，优先分配关系怎么办

原型在请求移除时，将它现有的优先空位转入 no_prefer 集合。以后其他子页被释放时，还会检查原来的优先请求是否仍存在。这种“空位优先给谁”的信息，与“子页里缓存着哪个前缀”是两套不同的信息。

依据：空位优先分配、借用与归还引用计数与释放后的状态

07 / PREFIX REUSE

先查每种缓存，再找共同恢复位置

第一步：相同前缀如何找到已有子页？

源码结论 对完整 token block，原型用前一块的前缀哈希、当前 token IDs、组标识等生成链式内容哈希。在对应组的缓存表中查 content_hash → 子页 ID。

命中时复用已有槽位并增加引用；如果该槽位原来在 evictor 中，就移出 evictor。没有命中则分配新槽位。“哈希条目存在”还不等于“这次能从那里恢复”：还需检查该内容已计算，以及类型的恢复约束。

第二步：每组给出“哪些长度合法”

缓存类型从长度 ℓ 继续计算时需要什么
Full Attentionℓ 之前需要的 KV 连续可用；不能跨过中间缺失的块。
Sliding Window Attention恢复边界所需窗口的 KV 可用；窗口之外更早的缺块不必一律否决该位置。
递归 / Mamba 状态该边界的所需状态可恢复，并满足 checkpoint / chunk 对齐；更早快照缺失不必否决更晚的完整快照。

真实代码中，get_possible_hit_lens() 返回端点均包含的区间列表，而不是每组只返回一个最大值。上层对区间集合求交，再从大到小检查所有组的 prefix_cache_alignment。

合法恢复集合 H = HFA ∩ HSWA ∩ Hstate ∩ …
最终 hit_len = H 中满足所有组对齐约束的最大长度
若不存在可用正长度，则从 0 开始

为什么不能只取各组最长值的最小值？

教学语义例子 请求长 13 个 token，FA block 与状态 checkpoint 间隔都设为 4。只看完整块边界 0、4、8、12：

长度FA 能否从此恢复状态能否从此恢复共同合法
0是，从头算是，初始状态是
4是，第 1–4 token 的 KV 在是，@4 快照在是
8是，第 5–8 token 的 KV 也在否，@8 快照不在否
12否，第 9–12 token 的 KV 不在是，@12 完整快照在否

所以 FA 的合法边界为 {0, 4, 8}，状态的合法边界为 {0, 4, 12}，交集是 {0, 4}，最终命中长度为 4。若只算 min(8,12)=8，会选中一个缺少状态的位置。

为什么没有 @8 快照还能有 @12？因为 @12 状态是对前 12 个 token 处理结果的摘要；它不是需要链接 @8 快照才能读取的差分。

Linear 管理器用 chunk / block 下标生成区间；checkpoint 的“处理完多少 token”还要结合模型状态写回路径核对。上面的集合解释恢复语义，不声称某个手写 bitmap 在作者代码中必然原样得到它。精确移植时应同时追踪状态写入时机、边界下标与恢复前的块表过滤。

第三步：共同长度确定后，整理每组的块表

源码随后调用各类型的 filter_computed_blocks_by_token(hit_len, ...)，按共同边界安排复用块、需要重算的后缀，以及 SWA / 状态类型不再需要的较早位置。它不只是返回一个数字给调度器。

08 / ALLOCATION

“有新大页额度”到底指什么？

源码结论 额度是本次分配允许该类型从全局池再取得多少张大页，或者通过整体驱逐取得多少张大页。它不是额外显存、不是 CUDA 新分配，也不是可以缓存多少个 checkpoint 的上限。

对每组 g，调度前估计需要 Rg 个子页，现有可供满足需求的小粒度容量为 Ug，每张大页能放 rg 个子页：

最少新大页 mg = ceil(max(Rg − Ug, 0) / rg)
最多新大页 Mg = ceil(Rg / rg)

原型的 U 包含“可直接分配的空位”与“驱逐旧前缀后能腾出的子页”；这两者都能用于满足需求，但后者需要牺牲缓存。计数时会扣掉已经作为整张可驱逐大页统计的子页，以免重复计算。

全局可用大页数 N原型选择
N ≥ Σ Mg给每组其最大新大页额度。
Σ mg ≤ N < Σ Mg给每组其最小新大页额度，更多利用现有类型内容量。
N < Σ mg无法按这次需求授予额度；该设置函数抛出空间不足异常。

这里的 N 包括全局已经空闲的大页，以及在两级前缀缓存模式下可整张驱逐的大页。各类型的配置容量上限也可能限制扩张；不能把上述算式当成唯一准入条件。

一个直观例子

某组需要 5 张子页，已有可用小粒度容量 2 张，每大页放 3 张：最少再要 1 张大页，最多再要 2 张。全局宽裕时给 2 张，紧张时给 1 张，并利用已有容量。

请求甲现在需要一张子页，分配器具体做什么？

先限定场景：要找的是某个缓存组的子页，例如 FA 组。下面的“其他请求空位”也必须能供这个组使用；另一种类型大页里的空位，不能不经整页回收就直接拿来。

1 · 先找空位，暂时不借优先给其他请求的空位
先看有没有“优先给甲”的空位；没有时，若甲获准为该组再取得大页且未达到组容量上限，就尝试从全局空闲池拿一张大页并取其中一个子页；如果本轮不走申请新大页的分支，则看有没有“没有指定优先请求”的空位。
这就是原文的“hashless + 亲和限制”：找无需驱逐的空位，这一轮不碰优先给乙等其他请求的空位。
2 · 上一步没拿到，且还有取得大页的额度：回收整张旧大页
从全局可整体驱逐的候选里选一张，删除其中保留的旧前缀，使整张大页回到空闲池。它可能原先属于其他缓存类型。
如果没有新大页额度，就跳过这一步。
3 · 再找一次空位，这次允许借其他请求的优先空位
重新尝试分配；上一步刚回收的大页可以在此变成当前组的子页。若走到借空位的分支，也允许拿“优先给乙、但乙尚未使用”的空位。
“放开亲和限制”只放开空位的优先关系，绝不表示抢走乙正在使用的子页。
4 · 仍然没有位置：牺牲一张本组保留的旧前缀子页
从本组“保留旧前缀、暂无请求使用”的子页中按策略选一张，驱逐旧前缀，再将其槽位用于新内容。若也没有可用受害者，则分配失败。
具体走一遍：甲没有新大页额度，乙有一个优先空位

假设甲没有自己的优先空位，也没有不指定优先请求的空位。第一步失败；第二步因无额度跳过；第三步允许借乙那个尚未使用的空位，因此分配成功。乙正在使用的任何子页都不会被动到。

顺序里有个容易忽略的地方：甲如果还有新大页额度，流程可能先在第二步牺牲整张旧大页，再到第三步拿位置；不一定会先借乙的空位，也不一定先只驱逐一张本组子页。额度会影响牺牲缓存的方式。

展开：用源码变量对照这四步
源码调用 / 字段对应中文过程
_maybe_allocate_hashless_block_id(..., affine_only=True)第一步：找可直接分配的位置，先不借其他请求的优先空位。
_maybe_evict_lv0_page()第二步：有额度时尝试整体驱逐大页。
_maybe_allocate_hashless_block_id(..., affine_only=False)第三步：重新分配，这次允许借其他请求的优先空位。
_maybe_allocate_evicted_block_id_level1()第四步：驱逐本组一张旧缓存子页。

小页分配器内部使用条件分支，并非每个分支失败后都继续尝试下一分支。例如本轮决定申请新大页，但全局没有空闲大页时，会先退出本轮调用，交回外层执行整页驱逐；不能理解为在同一次调用里又自动改去借其他空位。

展开：什么时候“显存看起来还有空位”也会失败？
  • 空位属于另一种类型，而且其所在大页还有活跃子页，不能整体转给当前类型。
  • 当前类型没有可用空位或可驱逐子页，且不能取得新大页额度。
  • 有理论可回收的字节，但不能组成当前实现认可的大页候选，或受到配置的类型容量上限限制。

因此应区分“GPU buffer 的总容量”“类型内可满足需求的子页”“可以跨类型转换的大页”。“驱逐失败”本身不等于 CUDA OOM；完整服务如何重调度或抢占还取决于调度器路径。

依据：最小 / 最大额度与授予四步分配控制流空位选择的内部顺序子页计数去重

09 / EVICTION

谁先被驱逐？两级分别看

第一层问题：谁有资格？

活跃引用先构成硬限制。子页进入普通缓存驱逐候选的前提是没有活跃请求引用。整张大页还需要满足更严格的条件。

假设一张大页里有 3 张子页。下面每一列都描述其中一张子页，不是在描述不同缓存类型。表中的“保留旧前缀”均指：旧内容有效，但当前没有请求使用。

第 1 张子页第 2 张子页第 3 张子页这张大页能怎样处理？
空位空位空位所有位置都可直接分配。最后一个子页释放成空位时，分配器可将整张大页归还全局池。
保留旧前缀保留旧前缀保留旧前缀三张子页均在驱逐候选管理器中；整张大页也成为候选。选中后先清除三个旧前缀的绑定，再归还整页。
正在使用保留旧前缀空位第 1 张仍有请求在用，不能回收整页。第 2 张可以按子页规则驱逐，第 3 张可以直接分配给同组请求。
保留旧前缀空位空位虽然没有请求在用，但本原型不自动把这个组合记作整页驱逐候选；候选计数要求每张子页都进入旧缓存驱逐管理器。
第三种与第四种组合的区别

第三种组合有请求正在使用，整页回收受到使用安全性的限制；第四种组合没有使用者，但“空位”和“保留旧前缀”由不同结构管理，当前原型的整页候选计数没有自动合并这两类位置。后者是实现条件，不能简单归结为“还有请求在使用”。

第二层问题：当前类型内，先驱逐哪张子页？

源码结论 排序键为 (last_accessed, -num_hashed_tokens, block_id)，取最小者。

  1. 优先驱逐最近访问记录更早的子页。
  2. 访问记录相同时，优先驱逐累计前缀长度更长的子页。
  3. 仍相同时，由 block ID 决定稳定次序。
候选last_accessed累计前缀长度次序
子页甲105122
子页乙101,0241
子页丙112,0483
子页乙→子页甲→子页丙

这里的“前缀长度”不是一张子页占多少字节，而是它位于多长的哈希前缀之后。先移除较深的位置，有利于避免在时间相同的情况下先破坏更浅的共同前缀；这不构成全局最优命中率保证。

第三层问题：全局先驱逐哪张大页？

只考虑每张子页都保留着旧前缀、且没有请求使用的大页。原型先在这些子页的 (last_accessed, -num_hashed_tokens) 中取字典序最大值，作为该大页的排序键；再在全局候选中选择最小的大页键。

大页键 K(P) = maxs ∈ P(last_accessed(s), −prefix_len(s))
驱逐候选 P* = arg minP 为符合条件的整页候选 K(P)

时间分量相当于由该大页里最近被访问的子页代表整页。如果存在同样最新的子页，第二分量再按字典序处理，不能简单地把全页最长前缀直接拼在最大时间后面。

大页 X：子页时间 [1, 100]

代表时间为 100。尽管有一个很冷的子页，另一个较热子页提高了整页保留优先级。

大页 Y：子页时间 [20, 30]

代表时间为 30。X、Y 都可驱逐且无其他差异时，先驱逐 Y。

全局选择跨越类型。FA 缺容量时，可能驱逐的是某张 Mamba 大页；随后这段容量才以 FA 子页大小重新切分。若只有当前类型的一个子页被驱逐，则直接复用该类型槽位，不会因此转换一整张大页。

“驱逐”具体改什么？

单子页路径移除旧内容哈希映射、更新 evictor / tracker，并把同一个槽位交给新内容。整张大页路径逐一移出其子页、删除对应缓存元数据，经小页释放使大页回到全局池，再由目标类型申请。它不是把旧 KV 自动迁移到 CPU，也不是调用 CUDA 卸载整块显存。

展开：为什么不能概括为普通 LRU

驱逐顺序同时受“有无大页额度、空位优先给谁、整页候选资格、两级排序、类型语义”影响。原型的 last_accessed 是软件 tracker 记录的逻辑时序，并非每次 GPU load 的硬件时间；SWA / Linear 的释放路径还会对不再需要的位置设置特殊优先级。因此“所有缓存统一按真实最近访问时间排序”是不准确的。

本路径没有默认加入 Marconi 的重计算代价评分。论文里的平衡与前缀对齐设计，以及原型采用的具体键值，需要分别论证，不能仅凭 “LRU” 标签推导全部行为。

依据：子页排序大页候选与聚合键跨组选择驱逐与哈希移除整页归还访问 tracker

检查点：“有一个热子页”影响大页排序；“有一个活跃子页”影响大页资格。前者是优先级，后者是硬限制。

10 / RESEARCH BOUNDARIES

现在能确认什么，还要验证什么？

Jenga 已经在处理异构缓存单元、共享容量、请求亲和、跨类型驱逐和恢复位置对齐。研究动机不宜写成“此前没有人发现混合缓存需要不同页大小”或“Jenga 没有考虑前缀依赖”。

可由现有证据确认不能据此直接宣称
子页管理与大页容量转换存在不同粒度。解耦后一定获得更高吞吐或更低延迟。
一个活跃子页会阻止所在大页整体转换。真实业务里这种情况占用了显著显存。
额度和分配顺序可能先触发整页驱逐。这种顺序一定比单子页优先更差。
跨类型共同命中位置可能比单组最大命中更短。所有丢失的命中都能通过新分配器挽回。

沿本周任务继续做，先量这三件事

  1. 容量卡在哪里：逐时刻统计“正在使用”“保留旧前缀但无人使用”“可直接分配空位”各占多少字节，并统计整页全空、整页均为无使用者的旧缓存，以及不同状态混合的大页；尤其记录“其他类型有空位，但当前类型无法扩张”的事件。
  2. 被牺牲的是哪些前缀：对每次整页驱逐记录触发类型、受害类型、各子页年龄、累计前缀长度、后续再次命中或重算；分开统计整页与子页驱逐的代价。
  3. 让同一请求的子页尽量集中是否仍有效：改变共享前缀比例与请求结束时差，测跨请求混放如何影响整页回收时间，再与固定预算下的基线策略对照。
一个可检验的问题表述

在共享前缀和请求生命周期差异较大的混合模型服务中，子页级复用与大页级容量回收之间的粒度差异，是否造成可观的容量滞留或额外重算？如果存在，减少它的收益能否覆盖元数据、寻址和搬移开销？

研究假设 上述是从代码约束推导出的测量方向，还不是“发现了一个新瓶颈”。需要先验证问题规模，再做固定模型、固定显存预算、固定请求轨迹下的消融；不能只比较命中率，至少还需同时报告重算 token / 时间、TTFT、吞吐与分配开销。

实现与实验边界

原型的两级路径、单页大小路径及其他实验分支不是同一套功能全集。这里审计的 CacheEngineV3 没有完整 CPU swap 支持，部分 sharing / copy 路径仍为未实现。本文的数值例子与交互演示不是 A800 实验结果，也没有证明原型对所有模型与 backend 的正确性。

展开：下次读代码的最短路线
  1. 先从模型注册找到真实的缓存组件、形状与 dtype。
  2. 看配置编译结果：每组有哪些组件、子页大小、LCM 大小、每页子页数。
  3. 跟一次请求：block table、执行块号变换、kernel view、状态写回边界。
  4. 跟一次命中：哈希匹配 → computed bitmap → 类型合法区间 → 交集 → 过滤块表。
  5. 跟一次失败分配：查大页额度 → 找优先给本请求的空位 → 检查整页候选 → 允许借其他请求的空位 → 驱逐本组旧缓存子页。
  6. 最后才用真实轨迹检验容量与重算是否显著。

用五句话复述整条链路

  1. 放什么：兼容组全部层的一个 token block 的 KV，或同一恢复边界的状态。
  2. 放哪里：逻辑块查组 block table，再由软件子页 ID 与层 / 元素偏移求 GPU 虚拟地址。
  3. 如何复用：哈希查槽位，各类型给合法恢复区间，求交并检查对齐。
  4. 如何驱逐：先确认没有请求在使用；实际流程还看能否取得大页、空位优先给谁，以及两级候选与排序。
  5. 如何转换类型：整张大页回到全局池后，才按另一种子页大小重新分配。
