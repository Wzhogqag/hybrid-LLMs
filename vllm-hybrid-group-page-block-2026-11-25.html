01

为什么要分 group？

Full 要留完整历史，SWA 只需窗口，linear 层保留状态。先按需求分开，再把需求相同的层合起来，减少重复管理。

不同需求，分开分配

Full 与 SWA 分开

同一请求的 Full 可能需要 7 块，SWA 只需 2 块。共用一张表会让窗口外空间也被保留。

相同需求，共享一张表

10 个 Full 层合组

它们要留的 token 范围相同，block table 可以共享；每层的 K/V 数值仍不同。

共享池，统一分配容量

把 20 个 SWA 层再拆开

拆成两个 10 层组，和 Full 组大小相同，池里的空闲块就能互相复用。

02

group、page、block，各自负责什么？

“page”在旧设计文档里也指过组的总大小。这里统一按源码的单层 spec 口径使用，避免混淆。

group

共享 block table 和分配规则的层集合。

例如：10 个 Full 层。不要求模型层编号连续。
page · p

一个层、一个 block ID 对应的存储。

Full 页装 B 个 token 的 K/V；linear 页装一份状态。
block ID

共享池中的分配与生命周期单位。

一个 ID 同时管理所属组内各层对应的页。
组块 Pg = Σ 组内各层的 p
池槽 S = max(Pg)，必要时再对齐
池 ID 数 N = floor(KV 预算 / S)

图中每格为一个 64 KiB 单层页；仅表示逻辑归属，是否地址相邻取决于 layout。

单层页没有另一套独立编号。指定一份页，用 （层，block ID）；同组不同层的 KV 数据并不相同。

池 ID 为 0…N−1，0 是 null 占位。各请求、各组共享同一池；同一普通活跃 ID 不会同时分给不同组。一个组释放后，其他组可复用其 ID 和空间。

token 数影响“领几块”，不是单块装下整条请求。 B=16 时，112 个 token 的 Full 历史需要 7 块；单层一块仍只有 16 个 token 的容量。

05

HBM 物理页，在另一层地址映射里

vLLM 的 page 是缓存组织单位；底层映射页是驱动与 GPU MMU 管理地址转换的单位。两者没有一对一关系。

vLLM / 软件索引
请求 + group→block table→block ID
层 + offset / stride→GPU 虚拟地址

得到的是 A + 偏移。vLLM 普通 cache manager 不查询“HBM 物理页 ID”。

编号仅为示意。虚拟地址连续，不保证底层物理位置连续。

实际硬件页尺寸：本次未测得。 取决于设备、驱动和分配/映射方式，不能从 1.53125 MiB 的 linear 页反推。一个 KV 页可跨多个底层映射页，相邻 KV 页也可能共享某个映射页的不同部分。

范围：固定版本普通共享 KV 池。容量数字为明确假设下的算术或既有记录；未追加引擎 / GPU 实验。不同 backend、TP、state dtype 与特殊池需单独核算。
