YOCO：架构、混合缓存与前缀复用

初版 2026-11-05 · 更新 2026-11-08 · 原论文、参考实现与 vLLM v0.30.0 源码对照

核心判断：YOCO 把“生成历史表示”和“读取历史表示”分到了模型的前后两部分。它显著减少全局 KV 的层间重复，却仍然需要管理前半部分的循环状态或滑动窗口。对混合模型 serving，关键变化是哪些状态必须保留、哪些可以重建，以及重建到底执行模型的哪一部分。

本文区分三类内容：带来源的公开事实、从计算依赖得到的推导、以及尚需实测的研究判断。所有具体 DeepSeek 数字仅针对公开的 DeepSeek-V4.1-Flash，不套用到其他 V4 / Pro 配置。未运行真实模型性能实验；附录的 CPU 小模型只验证依赖关系。

1. 先拆开三个容易混在一起的概念

概念 共享什么 解决什么问题
普通 KV cache 同一请求先前 token 的 K/V 后续生成无需重算全部历史
YOCO 的跨层共享 同一组历史 K/V，被多个网络层读取 减少层与层之间重复保存的 KV
跨请求 prefix cache 同一模型、相同前缀的缓存块和恢复状态 后来的请求跳过已完成的前缀计算

这三个机制可以叠加。YOCO 名字里的“once”指全局 KV 保存一份供后半部分读取，不是整台服务器只存一份缓存，也不是所有请求只计算一次。原论文明确说明 self-decoder 仍有自己的有界缓存。[1]

GQA/MQA 让多个 query head 共用 KV head；CLA 让若干层共用 KV；YOCO 则进一步组织前后半部分的计算，使一大段后续层不再产生历史 KV。原始 CLA 的典型设置是相邻层共享，并不自动带来“后半模型整体跳过 prefill”。[6]

2. 架构：前半部分写记忆，后半部分反复读取

原版 YOCO 有两部分：self-decoder 使用 gated retention 或 SWA；其输出产生共享全局 KV；cross-decoder 的每层以自己的 query 访问这份 KV。两部分均保持因果性。它于 2024 年 5 月提出，发表于 NeurIPS 2024。[1]

共享 KV 的 BF16 payload 为 2×N×8×128×2 = 4096N 字节。ABC 为 12 KiB，ABCD 为 16 KiB；长度 32,768 时为 128 MiB，长度 1,048,576 时为 4 GiB。这些数字无需再乘后半部分的 13 层。它们是按真实维度计算的逻辑 payload，不含分页填充、复制和临时激活。

每个 Self 层的循环矩阵为 [1,24,128,128]；13 层合计 5,111,808 个元素。若按 BF16 保存矩阵，完整状态包为 9.75 MiB；若按 FP32 保存则为 19.5 MiB。精度由实际实现决定，此处同时列出两种计费。一个历史 checkpoint 需要保存对应边界的完整状态包；当前请求连续执行时，直接使用 GPU 上已经更新的工作状态。

同一配置的 prefill 路径：A、B、C 经过前 13 层并形成共享 KV 与循环状态，可以跳过后 13 层；D 经过前 13 层、追加自己的共享 KV，再走后 13 层预测 E。实际 prefill 通常批量或分块执行，不要求将 A、B、C、D 分成四次 kernel 调用。

补充：普通 Full Attention 中，最后一层 hidden state 的用途

标准 decoder-only Transformer 中，D 的最终 hidden state 会用于预测下一个 token E。E 确定后，处理 E 的新一轮前向通常不再直接读取 D 的最终 hidden state，而是读取各层已保存的 D 的 K/V。

hDL → LM Head → E 的 token ID → Embedding(E)

这里同时存在另一条历史信息路径：第 ℓ 层处理 D 时，由该层输入（通常先经 Norm）生成并保存 KD(ℓ)、VD(ℓ)；处理 E 时，E 在第 ℓ 层的 query 读取这些 KV。最后一个 Attention 层的 KV 也由该层输入产生，不是把整网最终输出 hDL 再投影一次才得到。

“用于下一个 token”的具体含义标准 Full Attention
用 D 的最终 hidden state 预测 E 的分布会
E 已确定后，把 D 的最终 hidden state 额外拼进 E 的 embedding通常不会
E 计算时读取 D 留下的历史信息会，通过各层 K/V

以上讨论标准自回归前向，不把额外保存特征的推测解码、跨步 hidden-state 复用等扩展机制算入。

用符号表示，令 self-decoder 对 token t 的输出为 Mt。共享记忆由 Mt 经归一化、K/V 投影和相应位置编码得到；第 j 个 cross 层则从该层自己的输入计算 Qtj，读取位置不晚于 t 的共享记忆。

每层的 query、残差流、输出投影和 FFN 仍然不同，因此共享记忆不等于所有层输出一样。后续层可以带着不断更新的问题，反复检索同一份材料。参考实现的 CrossDecoder 在层循环外生成 K/V，在循环内将它们传给所有 CrossAttention。[2]

“decoder-decoder”也不表示生成两遍文本：输入一个 token，先经过 self-decoder，再经过 cross-decoder，最后预测下一个 token。生成出的 token 仍会在下一步进入前半部分。因果性保证旧前缀的表示不依赖后来的后缀，所以跨请求精确前缀共享依旧成立。

3. 为什么大部分 prompt 可以跳过后半模型？

设 prompt 为 A B C D，需要预测 E。下面是原版 YOCO 的一种合法执行方式：

位置 Self-decoder 生成共享 KV Cross-decoder
A、B、C 执行 保存对应 K/V 可以跳过
D 执行 保存 D 的 K/V 执行，读取 A…D 的共享 KV，预测 E
后续输入 E 更新自身状态 追加 E 的 K/V 执行，预测 F

推导原因：假设在 D 的第一个 cross 层要读取 A、B、C 的历史。它读取的是前半部分已经产生的共享 KV，没有依赖 A、B、C 在任何 cross 层的旧 hidden state。第二、第三个 cross 层同理，只需要 D 的前一层输出和同一份全局 KV。

因此跳过这些旧 token 的 cross 计算，不会丢失未来依赖。参考生成代码确实先对 prompt 的前 N−1 个 token 使用 skip_cross_decoder，再让最后一个 prompt token 完整前向以采样。[5]

有两个边界：

  • 请求每个 prompt token 的 logprob，或者训练时对所有位置计算语言模型损失，就需要这些位置的后半部分输出，不能照搬这种跳过方式。
  • 每次 decode 的当前 token 仍然要经过后半模型；多个 cross 层仍分别读取共享历史。容量只存一次，不代表 HBM 只读一次。实际读流量还受片上缓存和 kernel 实现影响。

所以，YOCO 的快 prefill 与跨请求 prefix caching 是两个独立维度：即使一个请求没有任何前缀命中，也能享受架构本身的 prefill 跳过；命中后还可以进一步少算前半部分。

先读左表：为什么一个是 L×N×D，另一个是 N×D + L×D？

普通 Full Attention：每层保存 N 个历史位置的 K/V，每个位置的表示宽度与 D 成比例，所以一层是 ND，L 层是 LND。此处把固定的 GQA 比例、K/V 两份和元素字节数省略了。

普通 Transformer：L 层 × N 个位置 × 每位置约 D 的宽度 → O(LND)

YOCO：全局 KV 只保存一套，因此这一项为 ND；各 Self 层仍有自己的有界状态，按论文固定局部配置的简写，每层与 D 成比例，L 层给出 LD。两种独立存储对象要相加：

一份全局 KV + 各 Self 层的局部状态
ND + LD = (N+L)D → O((N+L)D)

所以，N+L 并不是把“token 数”和“网络层数”当作同一种物理量直接相加：它是把两项存储规模 ND 与 LD 合并写在一起。更早的字节计费式 Ng + S 正好对应这两项：Ng 是共享 KV，S 是所有 Self 层当前状态。

这里也不能把 gRet 状态误认为只有一个 D 维向量。实际每层有多个矩阵；窗口宽度、每个 head 的维度等被当作固定配置，才出现这张简写表。详细维度在下方“更精确地展开”中说明。

再读右表：Full Attention 为什么多出一个 N？

Prefill 时，一层有 N 个输入位置，每个位置都要作为 query 读取此前的 key。把所有位置展开，相当于N 个 query × 约 N 个 key。每次 query-key 点积还要沿 head 的维度计算；各 head 合起来与 D 成比例，所以一层是 N²D，再乘 L 层。

L 层 × N 个 query × 约 N 个 key × 点积宽度 D
→ O(LN2D)

因果掩码只保留下三角。对于 ABCD，一层的读取关系为：

Query 位置Full Attention 需要读取的 key原版 YOCO 后半 Cross-decoder
AA：1 个该旧 prompt 位置可以跳过
BA、B：2 个可以跳过
CA、B、C：3 个可以跳过
DA、B、C、D：4 个只执行 D 的 query，读取同一套 ABCD 全局 KV

普通 attention 的合法 query-key 对共有 1+2+3+4=10 个；一般 N 时为 N(N+1)/2，增长阶仍是 N²。除以 2 不改变大 O。对 attention 概率再乘 V 也有相同的 N²D 量级，因此不会改变表中的阶。

YOCO 为什么可以写成 LND？两部分都要看

前半部分：gRet 不让每个新 query 显式扫描越来越长的全部历史，而是更新固定形状的循环矩阵。固定 head 维度后，每 token 的状态更新 / 读取成本不随此前 token 数增加，因此处理 N 个位置是线性增长。SWA 则是每个位置最多读取固定 W 个 key，一层为 NWD；W 固定后，同样对 N 线性。

后半部分：A、B、C 等旧 prompt 位置不需要执行 Cross-decoder；为了预测首个新 token，只需最后一个 prompt 位置的输出。一层由 N 个 query 各读 N 个 key，变成1 个 query 读 N 个 key，即 ND；所有 Cross 层合计仍是 LND 量级。

前半：N 个位置 × 固定形状的历史处理
后半：只保留末尾 query × N 个历史 key
两者都对 N 线性 → 表中 O(LND)

只共享 KV 不足以消掉 N²：如果后半部分仍对全部 N 个 prompt 位置做全局 attention，它仍有 N×N 个 query-key 关系。YOCO 还利用计算依赖，跳过了旧 prompt 位置的后半计算。D 的计算仍然会读取 A…D 的全局 KV；它没有放弃全局历史。

套到论文 26 层配置：前 13 层处理全部 N 个 token 并产生共享 KV 与循环状态；后 13 层只对末尾 prompt 位置产生所需输出。L/2 与 L 的系数差异、不同算子的常数，都被大 O 省略，不能拿“10 对与 4 对”直接预测整个模型的加速倍数。

只把输入长度 N 翻倍，其他配置保持不变普通 Transformer原版 YOCO
历史缓存KV 随 N 线性增长共享 KV 翻倍；一份当前循环状态或固定窗口容量保持不变
表中的 attention 计算增长长序列下约变为 4 倍约变为 2 倍
实际端到端 prefill 延迟还受 FFN、投影、带宽、批处理、kernel 和硬件利用率影响，不能直接按上面倍数换算
更精确地展开：被省略的窗口、head 维度和 ND² 在哪里？

以下为按张量维度补全的说明。设 Ls 为 Self 层数，Lc 为 Cross 层数；Dkv 为全部 KV head 的总宽度，Ds 为 Self 的总 head 宽度，dh 为每个循环 head 的维度，s 为元素字节数。

  • 普通 KV payload：同规格各层时，M = 2LN Dkvs。固定 GQA 比例下 Dkv 与 D 成比例，便简写成 O(LND)。
  • YOCO-SWA：M = 2N Dkvs + 2Lsmin(N,W)Dss。长度足够且 W 固定时，得到全局 ND 与局部 LD 两项。
  • YOCO-gRet：一层矩阵的元素数为 H dh² = Dsdh，所以其状态项更明确地写为 LsDsdhsstate。dh固定时对 Ds线性；若让每个 head 维度也随模型宽度增长，就应保留这个因子。
  • gRet 的历史混合计算：每层约 O(NDsdh)；SWA 为 O(NWDs)。固定 dh 或 W 后，都是对 N 线性。
右表限定的是 attention 模块，不是整网全部算子。Q/K/V 投影、输出投影、FFN 还要做逐 token 的稠密矩阵乘法；FFN 宽度与 D 成比例时，典型成本为 O(ND²)。原表标题虽写 Prefilling Time，表注限定了 attention modules。读取时必须保留这一范围。

例如，普通 dense Transformer 的完整 prefill 计算量通常包含 O(LND² + LN²D)：前项是稠密投影 / FFN 等，后项是全局 attention。YOCO 仍需计算前半部分全部 token 的稠密算子；最后一个 prompt 位置也要经过后半部分。其计算在固定模型配置下对输入长度 N 仍可线性增长，但不能因此把完整 FLOPs 直接写成原表的 LND。

这两张表也没有覆盖：模型权重与临时激活的总显存、批大小变化、额外保存很多历史 checkpoints 的成本，以及要求全部 prompt logprob / 训练时逐位置输出的情况。它们用于解释原版 YOCO 普通自回归生成路径的增长趋势。

4. 前半部分到底保存什么？

4.1 Gated retention：每层、每个 head 一份循环矩阵

简化一个 head 的更新：

St = γt St−1 + ktTvt
ot = qtSt

S 的大小由 head 维度决定，不随已经读过的 token 数增长。“constant state”说的是相对序列长度为常数，实际可能是较大的矩阵，并且有多层、多 head。参考代码按 Self 层分别维护 incremental_state，gated retention 的历史矩阵保存在 last_hidden_state。[3]

由更新式可以推出：

  1. 保存边界 p 的完整状态包 Cp，即所有 Self 层在同一前缀边界的状态，能够从下一个 token 继续。
  2. 只保存结束位置 N 的状态，不能一般地裁剪出更早 p 的状态。尤其新请求在 p 之后分叉时，CN 已混入错误后缀。
  3. 全局 KV 是前半部分最终表示的投影，不能一般地反推出所有较浅层的循环状态。投影可能降维，而且并未保存每层的中间结果。
  4. 有 Cq 且 q < p，可以沿相同前缀重放 q+1…p，得到精确 Cp；没有更早检查点时，可以从初始状态开始。

这里的“精确”指模型定义的计算等价。不同 GPU kernel、批大小或 scan 分块可能带来浮点误差，不能直接承诺逐 bit 相同。

4.2 SWA：每层窗口内的 KV

SWA 版本的 Self 层仍然各有自己的 K/V。参考实现为每层维护有界的 prev_key / prev_value，滑动窗口限制到固定范围。[4]

若边界 p 所需的各层窗口已经保存，恢复它们便可继续精确计算；不需要重新读完整前缀。

但如果这些窗口丢了，重新喂最后 W 个原始 token 不一般等于精确恢复。例如两层纯 SWA、窗口为 3（含当前 token）：

  • 第二层 token 8 的输出读取第二层位置 6、7、8 的 K/V。
  • 第二层位置 6 的 K/V 来自第一层位置 6 的 hidden state。
  • 第一层位置 6 又读取原始位置 4、5、6。
  • 因此重算第二层位置 8 的完整依赖覆盖原始位置 4…8，共 5 个 token。

对只有 SWA 与逐 token 运算的 m 层前半部分，单个输出的输入感受野最多为 1 + m(W−1)。恢复窗口时还要按目标缓存条目展开依赖；具体边界取决于缓存约定。这是有限依赖的推导，不是任意混合模型的通用 replay 长度。前半部分若含 full attention，局部 token 的精确重建还可能需要保留的全局历史 KV。

5. 显存：减少了全局 KV，也改变了检查点的相对成本

设全局 KV 每 token 占 g 字节，序列长度为 N，所有循环层的一个完整检查点共占 S 字节。忽略碎片、权重和临时激活：

结构 活跃请求所需缓存
L 层普通 full attention，假设各层 KV 大小相同 L × N × g
原版 YOCO-gRet N × g + S
原版 YOCO-SWA N × g + 所有 Self 层的窗口 KV

这是从存储对象逐项计数的结果。g = 2 × KV head 数 × head 维度 × 每元素字节数；gRet 状态则应按矩阵形状计费，不能直接当作一个 token 的 K/V。

对 prefix caching 的关键推导：活跃请求只需一份当前状态；想在很多历史边界恢复，就需要很多状态快照。每隔 I 个 token 保存一次检查点，历史状态总量约为 (N/I)S，而不是 S。

一个完全用于说明量级的例子，不是某款已发布模型的配置：

参数 / 对象 数值
共享全局 KV：8 个 KV head，head dim 128，BF16 4 KiB / token
16 个循环层，每层 16 head，128×128 矩阵，FP32 一个完整检查点 16 MiB
N = 65,536，只有共享全局 KV 256 MiB
同一前缀每 1,024 token 一个检查点 64 × 16 MiB = 1 GiB
同一前缀每 256 token 一个检查点 256 × 16 MiB = 4 GiB

在这个例子中，I = 4,096 时，全部历史检查点的总量就已等于共享全局 KV 的总量。分叉和跨请求去重会改变实际数量，但不改变检查点密度需要单独核算的事实。

若分配器还要求一份大状态和一个 KV block 使用相同物理分配单位，也可能迫使 token block 变粗或产生填充。YOCO 本身不会解决这个分配约束；它只是改变各类对象的数量与比例。此处是分配器设计层面的推导，不代表原版 YOCO 已被某个 vLLM Mamba allocator 原生支持。

6. 前缀复用：需要“全局历史”与“续算状态”两样东西

定义 G1:p 为前缀 1…p 的完整共享全局 KV，Cp 为原版 YOCO 前半部分在 p 的完整恢复状态包。先假设新请求在 p 后还有新 token：

保留了什么 能否直接从 p 后继续 合法的恢复方式
G1:p + Cp 可以 共享全局 KV，恢复状态，计算新后缀
G1:p + Cq，q < p 不可直接续算 从 q 重放前半部分到 p，再计算后缀
G1:p，没有可用循环检查点 不可直接续算 gRet 从初始状态重放前半部分；纯 SWA 可展开有限依赖
Cp，但较早全局 KV 有洞 不足以完成未来全局读取 从洞前的合法状态重建缺失 KV，或加载旧 KV
只有比 p 更晚、且已混入另一分支的检查点 不能用它恢复 p 寻找更早检查点或重新初始化

这回答了“checkpoint 有、KV 没有是否可能”：架构上可能，而且二者信息并不互相包含。某个缓存管理策略可以主动禁止这种驻留组合，但那是策略约束。对于原版 YOCO，前半部分的更新不依赖后半部分的全局读取，因此保存循环状态而淘汰部分全局 KV 是一种可表达的状态。

同样，“全局 KV 命中但循环状态丢失”不意味着这些 KV 在数学上无效，只意味着需要先修复续算条件。修复后仍可把它们交给 cross-decoder 使用。

如果整个 prompt 都命中且没有新后缀，还需要产生最后位置的 logits。单靠 KV 与结束状态不一定提供最后位置的当前 hidden state；可以额外缓存它，或像常见引擎那样保留最后一个 token 的重算。下面的例子始终带非空新后缀，避免混淆这个边界。

7. 一个贯穿例子：命中到 12，不等于省掉 12 个 token 的计算

旧请求处理了 x1…x12。新请求为相同前缀加上 x13、x14。缓存中 G1:12 都在，但只剩 C4。

  1. 恢复 C₄。各 Self 层回到相同前缀边界。
  2. 前半部分重放 x₅…x₁₂。重建 C₁₂；已有全局 KV 可以保持不动，省去重复投影 / 写入。这个阶段不需要旧 token 的 cross-decoder 计算。
  3. 前半部分处理 x₁₃、x₁₄。更新状态并追加两位置的全局 KV。
  4. 后半部分处理 x₁₄。读取完整共享历史，预测 x₁₅。这里只讨论普通生成，不要求 prompt logprob。

与完全未命中的、已经启用 YOCO 快 prefill 的基线比较：基线需要前半部分计算 1…14，恢复方案需要重放 5…12 并计算 13、14。主干前半计算只省掉了 1…4，另有历史全局 KV 投影和写入等收益。

若 C4 也没有了，gRet 需要从头重建状态。此时即使全局 KV token 命中率是 100%，仍可能重算几乎全部前半部分，实际收益要测量。全局 KV 命中率、直接可恢复前缀长度、实际跳过的执行量是三个不同指标。

还可以进一步沿算子依赖裁剪：若仅恢复循环矩阵、不需要重新产生某些旧 token 的全局 KV，顶端 Self 层的部分 readout / FFN 可能无需执行。这是从状态更新依赖推导的优化方向，尚未作为真实实现验证，也不据此声称新颖性。

8. 为什么原版 YOCO 的恢复与交错混合模型不一样？

原版 YOCO 的前半部分仅含有界状态的 token mixer，后半部分只消费共享全局 KV。因此恢复前半部分时，不必执行后半部分，也不必读取后半部分的全局 KV。

对于 full attention 与 recurrent 层交错的模型，更深 recurrent 层的输入可能经过 full attention；精确重放时仍需要相应的历史 attention 依赖。两种结构都能谈“重放”，但运行的子图、历史读取量和成本不同。

对于 Gemma、DeepSeek 等 YOCO 相关变体，则必须重新检查哪些层拥有自己的持久状态、共享的是 hidden state 还是物理 KV、消费者是否有额外 SWA。不能只看名字就套用原版的复杂度或恢复合同。

9. 驱逐与分配：真正要管理的是哪些对象？

对象 存储与访问特点 驱逐后的后果
全局 KV block 一个物理 owner 可有多个消费层，还可被多请求共享 后续全局读取需要先补洞或加载
循环检查点 表示一个前缀边界；一次恢复只需一个完整状态包 增加状态重放距离，不一定使全局 KV 失效
SWA 窗口状态 每层有界；可能保存、精确重建或采用近似重放 由具体恢复规则决定可复用性
当前活跃状态 不断更新；分支开始时需保留正确快照 不能误覆盖其他请求 / 分支仍使用的状态

由这些依赖可以推出几个系统要求：

  • 按物理 owner 计费。十个层引用同一 KV，不应计成十份显存，也不应以“逐层驱逐”删除同一个底层对象。多个请求的共享引用同样要管理。
  • 状态与全局 KV 分开记录驻留。统一 token 前缀身份，不意味着所有缓存对象必须绑定为一个不可拆的物理包。
  • 驱逐价值取决于恢复计划。丢一个中间检查点可能只增加少量前半重放；丢早期全局块可能影响大量后续读取。反过来，便宜可重建的 KV 也未必总值得保留。
  • 区分活跃状态和历史快照。循环状态通常原地更新；两个分支从同一 checkpoint 开始后，要有独立工作状态或写时复制。
  • 维护复用身份。模型权重、适配器、位置 / 掩码语义、KV 表示格式等必须兼容；相同 token 块出现在不同前文后，通常不能仅凭块内 token 复用。

一个可评估的恢复选择不是“命中 / 没命中”两档，而是：直接恢复、从较早检查点精确重放、加载异地状态、重建 KV 缺口，以及在模型明确支持时选择近似恢复。成本应计入传输、状态复制、重放算子、最终 attention 读取和实际批处理形状。

10. vLLM：已支持什么，以及没有证明什么？

“2024 年已经在 vLLM 上有”需要拆开理解：2024 是 YOCO 原论文年份；本次核实到的 V1 通用跨层共享和模型快 prefill 合并记录集中在 2025 年及以后。研究用实现、某个模型支持、原版 YOCO 原生支持、以及 prefix caching 完整支持，不是同一个声明。

Gemma3n 快 prefill PR #22628 2025-08-28 合并
Gemma4 快 prefill PR #38879 2026-04-06 合并

v0.30.0 中三处代码把机制说得很清楚：

  1. Attention 层通过 kv_sharing_target_layer_name 指定缓存 owner。
  2. GPUModelRunner.get_kv_cache_spec() 对消费层跳过独立 KVCacheSpec；initialize_kv_cache_tensors() 让消费层的缓存引用指向 owner 张量。
  3. Gemma3n 的共享层只产生 Q，K/V 交给目标层提供；开启快 prefill 时，模型另外选择需要 logits 的位置进入 cross-decoder。[10] [11]

kv_caches[layer_name] = kv_caches[target_layer_name]
attn_output = self.attn(q, None, None)

--kv-sharing-fast-prefill 控制的是被模型实现接入的快 prefill 路径，--enable-prefix-caching 控制跨请求复用。两者分开评估，不能把打开前一个开关当成“任意模型自动变 YOCO”。v0.30.0 的 runner 对快 prefill 与 prompt logprob 的组合有明确限制。旧文档中“仍无 prefill 收益”的描述也不能覆盖后来已合并的模型实现。[10] [12]

另外，Phi4FlashForCausalLM 在 v0.30.0 注册表中属于 previously supported，记录的最后支持版本是 0.10.2；相关 V1 移植议题和恢复 PR 仍需按实际状态判断。不能因为 2025 年论文用过 vLLM，就认为你现在的 v0.30.0 可以直接运行该模型。[13] [14]

这些案例支持“跨层共享已被多家团队采用”，但不支持“未来模型都会采用原版 YOCO”。跨层表示共享牺牲了部分独立表示能力，需要训练配合；不能直接把现有普通 Transformer 的逐层 KV 合并而保持原模型函数不变。SwiftKV 等工作则明确研究了通过模型变换与蒸馏适配现有模型的另一条路线。[20]

DeepSeek 的 128-token replay 必须单独理解

DeepSeek-V4.1-Flash 模型卡给出 20 层 causal encoder + 20 层 decoder 的 CED 结构。DeepInfer 的部署说明进一步公开：encoder SWA 状态缺失时重放近期窗口；decoder SWA 则用 prompt 尾部重放恢复，其结果用于后续 decode，不进入 prefix cache。[17] [18]

文档明确把 128-token SWA bounded replay 生成的窗口称为近似状态，并说明 20 层 decoder 的完整依赖恢复需要更长的约 2,560-token 区域。这里的 2,560 是该实现给出的量级，不能替代任意模型的依赖计算。

这有两个研究含义：第一，“SWA 缺失但全局 KV 存在”的修复路径已经有生产公开实例，不能再笼统说成现有方案都无法使用。第二，你若保持精确复用目标，就要把精确状态恢复和近似窗口重放作为不同语义的基线，分别报告性能和质量。

12. 对当前课题，更有价值的切入点是什么？

我的判断是：YOCO 使“恢复计算的子图”成为混合缓存管理必须理解的一部分。只统计缓存类型与驻留字节，无法判断一个不完整命中到底值多少钱。

一个更具体的系统问题可以表述为：

在同时存在跨层 KV 共享、循环状态和窗口状态的模型中，运行时如何识别合法恢复路径，并在存储、加载与重放之间选择代价合适的方案，使残缺的前缀缓存仍能产生可衡量的收益？

这不是直接给出一个已证明的新论文方向。已有工作边界相当重要：

  • Marconi 与 Sparse Prefix Caching 已研究混合模型缓存与检查点问题；仅改变 checkpoint 间隔或淘汰评分，很难单独构成完整新故事。
  • HiState 于 2026-10-30 发布预印本，已经覆盖检查点跨层级保存、自适应间隔与协调驱逐，并在 vLLM 上评估 agent traces。分层保存检查点本身不能当作空白。[21]
  • DeepSeek 的 bounded replay 已覆盖一类缺失 SWA 的近似修复。新的系统需要说明所支持的拓扑、精确性合同、代价模型和执行范围有什么实质区别。

最值得先做的三个实验，保持一个 GPU、短运行时间即可：

实验 控制什么 想回答什么
状态缺失 / KV 缺口微实验 固定相同 token 前缀，分别删除 checkpoint、窗口和全局块 哪些缺失组合能精确修复？必须执行哪些层与算子？
固定总显存的 checkpoint 密度扫描 固定总缓存预算，而不是额外赠送状态空间 更密检查点节省多少 replay，又挤出多少可复用 KV？
命中率与实际收益解耦实验 比较直接恢复、较早检查点重放、已有快 prefill 的未命中基线 高 KV 命中是否真的省了主干计算、降低了 TTFT？

记录全局 KV token 命中率、直接状态命中边界、实际重放 token / 层 / FLOPs、每类对象的常驻量、传输与复制成本，以及 p50/p95/p99 TTFT。近似恢复另测质量。硬件成本最终由真实 kernel 和调度测量，不把 FLOPs 自动等同于延迟。

若沿用 vLLM v0.30.0，Gemma3n / Gemma4 的小尺寸 KV-sharing 配置可用于验证跨层别名、SWA 和快 prefill；原版 gRet 的循环恢复仍需对应实现接入。不要把一种模型的结果直接解释成所有 YOCO 变体的结果。

13. 论文效果应该如何读？

原论文用 3B 主实验、不同规模的训练曲线和百万上下文检索等结果支撑可行性，并报告长上下文 prefill 的显著收益。这些是特定模型与实现下的结果，不是 prefix caching 在真实 agent 负载中的端到端收益。[1]

评估时尤其要记住：低缓存容量、低 decode 带宽、低 prefill 时间、模型质量是不同维度。YOCO 主要减少历史表示的存储冗余，并允许裁掉不需要的 prompt 计算；它仍保留多层读取历史的开销，也需要训练适应共享表示。SambaY 正是在减少 decoder 的昂贵历史读取这一方向继续改造。[15]

"""Small numerical checks of YOCO dependencies, not a trained-model benchmark."""
import copy
import json
import numpy as np

rng = np.random.default_rng(7)
dim = 6
layers = 2
self_weights = [tuple(rng.normal(scale=0.18, size=(dim, dim)) for _ in range(4)) for _ in range(layers)]
cross_weights = [tuple(rng.normal(scale=0.18, size=(dim, dim)) for _ in range(3)) for _ in range(layers)]
wk, wv = (rng.normal(scale=0.18, size=(dim, dim)) for _ in range(2))
tokens = rng.normal(scale=0.5, size=(18, dim))

def produce(x, states):
    x = x.copy()
    next_states = []
    for old, (q, k, v, o) in zip(states, self_weights):
        state = 0.91 * old + np.outer(x @ k, x @ v)
        x = np.tanh(x + (x @ q) @ state @ o)
        next_states.append(state)
    return x, next_states, x @ wk, x @ wv

def consume(x, keys, values):
    for q, o, ff in cross_weights:
        scores = keys @ (x @ q) / np.sqrt(dim)
        probs = np.exp(scores - scores.max())
        probs /= probs.sum()
        x = np.tanh(x + probs @ values @ o)
        x = x + np.tanh(x @ ff)
    return x

def run(xs, states=None, keys=None, values=None, all_queries=False):
    states = [np.zeros((dim, dim)) for _ in range(layers)] if states is None else copy.deepcopy(states)
    keys = [] if keys is None else [x.copy() for x in keys]
    values = [] if values is None else [x.copy() for x in values]
    history = []
    for i, tok in enumerate(xs):
        x, states, k, v = produce(tok, states)
        keys.append(k)
        values.append(v)
        if all_queries or i == len(xs) - 1:
            answer = consume(x, np.asarray(keys), np.asarray(values))
        history.append((copy.deepcopy(states), [x.copy() for x in keys], [x.copy() for x in values]))
    return answer, history

full, history = run(tokens, all_queries=True)
fast, _ = run(tokens, all_queries=False)
c, p = 5, 13
states_c, _, _ = history[c - 1]
states_p, keys_p, values_p = history[p - 1]
_, replay = run(tokens[c:p], states_c)
replayed_states = replay[-1][0]
continued, _ = run(tokens[p:], replayed_states, keys_p, values_p)
_, short_replay = run(tokens[p - 3:p])
wrong_continued, _ = run(tokens[p:], short_replay[-1][0], keys_p, values_p)

def swa_stack(xs, window=3):
    x = np.asarray(xs, dtype=np.float64)
    for layer in range(2):
        y = []
        for i in range(len(x)):
            a = x[max(0, i - window + 1):i + 1]
            scores = a * x[i] * (0.3 + layer * 0.1)
            probs = np.exp(scores - scores.max())
            probs /= probs.sum()
            y.append(np.tanh(x[i] + probs @ a))
        x = np.asarray(y)
    return x

xs = np.asarray([0.2, -0.7, 0.3, 0.8, -0.4, 0.6, -0.9, 0.1])
target = swa_stack(xs)[-1]
result = {
    "scope": "synthetic CPU mechanism checks; no real YOCO weights or performance measurements",
    "prefill_skip_max_abs_error": float(np.max(np.abs(full - fast))),
    "checkpoint_replay_state_max_abs_error": float(max(np.max(np.abs(a - b)) for a, b in zip(states_p, replayed_states))),
    "checkpoint_replay_last_output_max_abs_error": float(np.max(np.abs(full - continued))),
    "gated_recurrence_reset_and_replay_only_3_tokens_output_error": float(np.max(np.abs(full - wrong_continued))),
    "swa_2_layers_window_3_replay_3_tokens_last_output_error": float(abs(swa_stack(xs[-3:])[-1] - target)),
    "swa_2_layers_window_3_replay_5_tokens_last_output_error": float(abs(swa_stack(xs[-5:])[-1] - target)),
    "illustrative_memory": {
        "global_kv_bytes_per_token": 2 * 8 * 128 * 2,
        "checkpoint_bundle_bytes": 16 * 16 * 128 * 128 * 4,
        "global_kv_at_65536_tokens_bytes": 65536 * 2 * 8 * 128 * 2,
        "checkpoint_bytes_at_interval_256": (65536 // 256) * 16 * 16 * 128 * 128 * 4,
    },
}
assert result["prefill_skip_max_abs_error"] == 0
