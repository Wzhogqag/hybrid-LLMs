Hybrid KV Cache 分组管理与 Metadata 开销

阶段性结论整理：从 Group、Block Table 与 Attention Metadata 的关系出发，梳理 vLLM 已有优化实践、真实性能证据，以及对细粒度缓存管理设计的启示。

Executive summary

核心结论

增加 KV Cache Group 会带来额外运行时开销，但 Group 数量并不必然等比例转化为 Metadata 构建开销。

vLLM 已有工作表明，可以通过公共 Metadata 预计算、跨 Group 复用，以及批量计算 Group-specific 索引来控制多 Group 开销。因此，细粒度缓存管理不必简单地以牺牲 Group 数量为代价。

缓存管理粒度

哪些层或状态可以独立驻留、驱逐、分配物理块和恢复。

Metadata 计算粒度

哪些计算可以跨 Group 共享，哪些物理映射和状态字段必须独立维护。

阶段性设计原则：将缓存管理粒度与 Metadata 计算粒度解耦；共享公共计算，但保持 Group-local 物理映射、状态索引和 Checkpoint 依赖的正确性。

1. 为什么需要 Group？

Hybrid 模型不同层可能具有不同的缓存状态与内存需求，例如：

Full Attention

保存完整 KV Cache，通常按 Attention KV block 管理。

SWA

只需要满足滑动窗口语义的 KV 数据，缓存范围和复用约束不同。

Mamba / GDN / SSM

需要维护 recurrent state 或 checkpoint，恢复依赖状态位置与合法恢复点。

KV Cache Group

将缓存规格兼容的层组织起来，分别管理相应的缓存块及运行时映射。

Group 不只是逻辑分类，也影响 Block Table、物理块分配以及状态索引等运行时结构。

Group 数量增加后，系统可能需要维护更多 Block Table、状态索引和 Group-local Metadata，并执行更多更新操作。但这不意味着所有公共计算都必须重复执行。

2. Block Table 与 Attention Metadata：必须区分

2.1 Block Table：描述物理缓存映射

Block Table 记录请求逻辑缓存块与物理 Block ID 之间的映射。可以将不同 Group 的映射简化为：

同一请求的逻辑 Block，在不同 Group 中对应不同物理 Block

逻辑 Block 序列

B0
B1
B2
B3

Group 0 Block Table

[12, 18, 25, 31]

Group 1 Block Table

[42, 47, 51, 63]

示意数据，仅用于说明不同 Group 可具有独立物理映射。实际维度取决于执行路径。

在讨论的 vLLM 实现中，MultiGroupBlockTable 管理多个 Group 对应的 Block Table。典型 Block Table Tensor 可抽象为：

[ max_num_reqs, max_num_blocks_per_req ]

其中保存物理 Block ID，通常使用 int32。Block Table 与物理缓存布局紧密相关，不能因为 Metadata 可共享，就认为 Block Table 也可以直接共享。

2.2 Attention Metadata：描述本轮计算所需信息

Attention Metadata 是 Attention Backend 在执行模型计算时需要的信息集合，可能包括当前 batch 的请求数、序列长度、Query/KV 位置与长度、Block Table 相关信息、Slot Mapping 以及其他辅助 Tensor。它不是固定形状的单一 Tensor，而是由具体 Backend 的 Metadata Builder 构造。

数据结构主要作用跨 Group 共享原则
Batch-level Metadata描述当前 batch 的公共计算信息通常可共享
Block Table描述 Group 的物理缓存映射通常需独立
Group-specific State Index描述某个 Group 对应的状态位置保持 Group 对应关系
Checkpoint 映射指定状态保存或恢复的位置必须保证本组正确性
Mg = Mcommon + Mgroup,g

这是一种理解 Metadata 的抽象分解：公共部分跨 Group 复用，Group-local 部分仍需按组维护。

3. vLLM 已有的优化演进

目前找到的工作可以串成一条路线：消除重复公共计算 → 复用公共 Metadata → 批量计算 Group-specific 字段。

3.3 PR #58851：跨 Group 批量计算 Mamba / GDN / KDA Metadata

[Perf][MRV2] Share GDN, Mamba and Kimi-K3 KDA batch metadata across KV cache groups 当时为 Open PR

该 PR 将 #58762 的思路扩展到 Kimi-K3 KDA 和 speculative Mamba 等场景。一个具体实现是：将多个 Group 的 Mamba aligned state indices 通过一次 Triton Kernel 批量计算。

[ num_groups, max_num_reqs, 1 + num_speculative_blocks ]

输出 Tensor 的三个维度分别对应 Group、Request，以及状态索引 / speculative block 相关索引。计算完成后，将不同 Group 对应的切片交给各自 Builder。

这不是多个 CPU Builder 并行执行，而是把多个 Group 的 GPU 索引计算合并为一次批量 Kernel。#58851 在现有记录中仍是 Open PR，不应描述为已进入正式 main。

4. 真实性能问题：Group 增加的开销确实存在

Issue #60008：Hybrid Mamba prefix caching performance overhead

该 Issue 对 Nemotron-3.5-Lightning、Model Runner V2 的运行时做了 profiling。实验使用 4×GB200、随机 8K input / 1K output，并且没有实际 Prefix Cache 命中。开启 Mamba prefix caching 后仍观察到显著开销。

4.1 主要开销来源

Group-specific Block Table 操作

4 个 Mamba Groups × 每组约 7 个 Torch 操作，形成约 28 次额外 eager launches。

CUDA Graph 外的 align Kernel

部分每 step 的对齐计算不在 CUDA Graph 中，增加 CPU/GPU 调度开销和 GPU idle。

Prefill 切分

Block Boundary 对齐可能造成额外 prefill split，影响 TTFT，不能将全部损失归结为 Metadata Builder。

Group 数量放大重复工作

若每组独立执行索引与映射操作，Group 数增加会增加 Kernel Launch 和调度成本。

4.3 重要正确性教训：Checkpoint Metadata 不能无差别共享

Issue #60008 还记录了一个静默数据错误：尝试将 Metadata 复用与 Mamba2 内部 Prefill Checkpoint 结合时，某些 Group 复用了首个 Group 的 checkpoint metadata，导致后续 Group 可能将 checkpoint 写入首个 Group 的物理 Block。

原因在于：部分 checkpoint metadata 字段依赖具体 Group 的 Block Table。它们不是公共 Batch Metadata。

正确性约束：公共 Batch 信息可以共享，但物理映射、Checkpoint 目的位置、State Index 和恢复依赖必须保留 Group-local 对应关系。

5. 对我们的分层驱逐设计意味着什么？

5.1 分层驱逐要求物理映射具备独立性

假设一个 Group 中包含 4 个 Full Attention 层。如果 4 层共享同一套 Block Table，那么仅靠这张表通常无法表达“Layer 1 已驱逐、其他层仍驻留”这种完全独立的物理缓存状态。

目标：层级缓存状态可以独立变化
Layer 0
驻留
Layer 1
已驱逐
Layer 2
驻留
Layer 3
驻留

示意：需要某种 per-layer 物理映射、有效性状态或更细粒度 Group 机制来表达。

可能的实现方向包括：

  1. 将原有 Group 拆成更细粒度的 Group，各自维护 Block Table。
  2. 保留较大的逻辑 Group，但增加 per-layer 物理映射或有效性间接表。

两种方案的具体成本不同，但都要求不能再假设一张共享 Block Table 足以描述所有层的独立缓存映射。

5.2 管理粒度与 Metadata 构建粒度可以解耦

假设把 16 个层拆成 16 个 Group：

  • 16 个 Group 可以具有独立的缓存分配和驱逐状态。
  • 16 个 Group 可以具有各自的 Block Table。
  • 但它们不一定需要 16 次完整的 Batch Metadata 构建。
Mg = Mcommon + Mlocal,g
Metadata 部分建议处理方式
Common Metadata当前 Batch 公共信息，计算一次并跨 Group 复用
Group-local Mapping各 Group 的 Block Table 信息独立更新
Group-local State状态索引、Checkpoint 位置等保留各自映射
批量索引计算兼容字段尽可能合并为一次 GPU Kernel
关键认识：缓存管理层面可以采用细粒度 Group；计算层面则通过共享公共 Metadata 和批量更新控制开销。二者不必绑定。

5.3 共享 Metadata 不等于共享缓存状态

Full Attention KV、SWA KV、Mamba/GDN recurrent state 的恢复依赖并不相同。即使多个 Group 能复用公共 Batch Metadata，也不意味着它们可以共用物理 Block 映射、Checkpoint 位置、State Index、驻留状态或恢复合法性信息。

对我们的方案，正确性约束应当是：共享计算所需的公共信息，而不是不同缓存状态的物理身份和恢复依赖关系。

6. 关于 CPU 并行 Builder：当前证据支持什么判断？

此前讨论过是否可以让多个 Group 的 Metadata Builder 并行执行。结合目前找到的真实实现，需要调整该方向的优先级。

目前没有足够的 vLLM Issue 或 PR 证据证明，多线程并行执行多个 CPU Builder 是解决 Group Metadata 开销的主要有效路线。社区实际采用的优化路径是：

优化方向代表工作核心思路
消除公共计算重复#52297公共 Metadata 预计算一次
跨 Group 复用#58762首个 Group build，后续 Group update
批量计算 Group-specific 字段#58851多个 Group 的索引通过一个 Triton Kernel 计算
融合 Block Table 操作#58737，见 #60008 讨论减少 Torch 操作和 GPU Launch
目前更有依据的优先级是：先消除重复计算、复用 Metadata、批量化 GPU 操作；CPU 多线程并行 Builder 暂时不是首要方向。这不等于 CPU 并行绝对不可行，而是尚缺乏足够的实证支持。

7. 结论边界与版本说明

  • 不是所有 Group 都能共享 Metadata：#58762 的复用依赖兼容的 Spec、Builder 类型和更新接口。
  • 已有优化没有解决任意层级独立驱逐：这些工作主要优化 Metadata 与索引计算，不等于已经实现任意层级的缓存驻留、驱逐和精确恢复。
  • PR 状态需要区分：#58762 已合并；#58851 在当前掌握记录中为 Open PR；#60008 是性能分析 Issue。
  • 性能数据不能直接外推：相关数据主要来自 H200、B200、GB200 等环境，与本地 A800 环境不同。
  • 当前代码版本：vLLM 0.30.0，commit ced6857afa0ea7b2e3f0846a62e1394e90f15607。上述后续 PR 的优化不能假定已存在于该 commit，需要单独核对或移植。

总结页：可以直接用于汇报

Hybrid LLM 的细粒度缓存管理可能需要增加 KV Cache Group，以支持不同层或不同缓存状态的独立驻留、驱逐和恢复。但 Group 数量增加会带来额外的 Block Table 管理、Metadata 更新及 GPU Kernel Launch 开销。

vLLM 的已有工作表明，这些开销并不必然随 Group 数量线性增长。通过公共 Metadata 预计算（#52297）、跨 Group Metadata 复用（#58762）以及批量计算 Group-specific 索引（#58851），可以显著降低多 Group 管理成本。真实 profiling（#60008）也验证了这些优化对 GPU idle、Host span 和执行开销的改善。

因此，我们的设计不应简单地在缓存管理粒度和运行时开销之间做取舍，而应将两者解耦：缓存管理层面允许不同层独立管理，计算层面尽可能复用公共 Metadata，同时严格保留各 Group 的物理映射、状态索引和 Checkpoint 依赖关系。

三个需要记住的概念：

  1. Group 是缓存管理的组织单位，不意味着所有计算都必须独立执行。
  2. Metadata 可以共享，但 Block Table 和状态恢复依赖必须保持正确的 Group 对应关系。
  3. 真正值得研究的不是如何减少 Group，而是如何在细粒度管理下消除 Group 间的重复工作。
