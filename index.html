1. 先建立模型：树里存的是什么

Marconi 面向的是同时含 Attention 层和递归式 SSM/Mamba 层的混合模型。前缀缓存命中时，系统希望复用已经算好的状态，跳过重复的 prefill 计算。

Attention：KV Cache

保存前缀 token 对应的 Key/Value。KV 大体随序列长度增长：前缀越长，KV 通常越多。

Mamba / SSM：递归状态

保存处理完某段前缀后的状态。对给定模型配置，状态大小通常不随此前 token 数线性增长；但重算长前缀的状态可能很贵。

Radix Tree 把共享前缀组织成树。一个节点的 value 通常表示该节点自己负责的一段 token，而不是整条从 Root 开始的路径。沿 Root 到节点的路径拼起来，才是完整前缀。

Root
↓
A：共享前缀
↙
B：分支 1
↓
C：叶子
↘
D：分支 2
↓
E：叶子

示意图。真实 Radix Tree 的一个节点可以包含多个 token；节点边界由压缩前缀树的分叉与插入过程决定。

后面所有公式的关键：候选节点的计算收益通常按“当前节点相对父路径额外提供了什么”来估算，而不是把祖先已经能提供的收益重复算到每个后代节点上。

2. 普通 LRU 为什么常从叶子驱逐

LRU 的定义是优先淘汰最近最少使用的缓存项；它本身并没有规定必须删除叶子。树状前缀缓存的常见实现会把候选限制为叶子，以便删除操作简单且不会破坏仍然存在的后代路径。

为什么叶子比较容易删？

  • 叶子没有子节点，删除时只需从父节点的 children 中移除它，并释放对应缓存状态。
  • 若直接删一个有多个子节点的内部节点，后代路径就会失去中间连接，必须额外重组树；而该内部节点可能代表多个请求共享的前缀。
  • 叶子删除后，如果父节点不再有任何子节点，父节点也变成叶子，可以被放进候选集合，继续参与后续驱逐。

Marconi 仓库中的基线 evict_v1() 注释写着 “LRU on the leaf nodes”，并通过收集叶子、按时间优先级弹出、删除叶子来实现。因此准确说法是：这份实现的 V1 限定从叶子候选中做 LRU，而不是 LRU 理论上必然从叶子开始。

leaves = self._collect_leaves()
heapq.heapify(leaves)

while bytes_evicted < bytes_to_remove and leaves:
    x = heapq.heappop(leaves)  # 取最旧候选
    self._delete_leaf(x)

    if len(x.parent.children) == 0:
        heapq.heappush(leaves, x.parent)

以上是突出控制流程的摘录式示意，便于阅读；请以仓库当前版本的完整函数为准。

3. Marconi 如何驱逐只有一个子节点的内部节点

Marconi V2 的候选不只有叶子，还包含恰好有一个子节点的节点。源码的候选筛选逻辑可概括为：

if len(cur_node.children) in [0, 1] and cur_node.value is not None:
    candidates.append(cur_node)
节点子节点数是否候选直觉
0是，叶子可以直接移除该分支及其状态。
1是，单子节点内部节点可以释放这个中间检查点的 SSM 状态，并把路径与子节点合并。
2 个或更多通常不选该节点是多个分支共享的前缀，直接移除会影响多条路径。

单子节点为什么可以合并？

驱逐前
父路径
↓
P：token 段 P
SSM(P) + KV(P)
↓
C：token 段 C
SSM(C) + KV(C)
驱逐 P 后（概念图）
父路径
↓
合并后的节点
token 段 P + C
保留 C 的混合状态

代码中的关键操作可概括为：

new_node.value = node.value + child.value
new_node.hybrid_states = child.hybrid_states
new_node.children = child.children
new_node.parent = node.parent

这意味着路径表示合并，合并后保留子节点的状态。对混合缓存而言，被驱逐中间节点的 SSM 状态被释放；子节点代表更长前缀的状态仍可保留。KV 路径/元数据会随节点重组而变化，不能把它简单描述成“只把一个字段设为 None，其他一切完全不动”。

准确表述：驱逐单子节点内部节点时，释放该中间节点自身的 SSM 状态，并将其 token 路径与子节点合并、保留子节点的混合状态。叶子节点的驱逐则是移除叶子及其对应缓存状态。

4. 计算收益：保留它能少算多少 FLOPs？

这是最重要的一步。想象一个请求有 120 个输入 token，其中前 100 个 token 已经通过父路径覆盖；候选节点自身额外覆盖 20 个 token。

Ltotal = 120，　Lparent = 100，　Lnode = 20

当候选节点命中时，系统不需要从头重算完整的 120-token 前缀。父路径已覆盖的部分不应该再全部记到这个候选节点名下；该节点的收益要衡量它相对父路径增加了多少可避免计算。

4.1 Mamba / SSM 的计算收益

FSSM(n) = NSSM × FMamba(Lnode)

N_SSM 是 SSM 层数；F_Mamba 是实现中用于估算 Mamba 处理指定长度 token 的 FLOPs 的函数。节点自身长度是 20，因此这个估算主要按这 20 个 token 的 SSM 计算来算。

为什么长前缀可能很值钱？SSM 状态占用对固定模型配置通常近似固定，但从头处理更长 token 段的计算会增加。因此，固定大小的状态若能避免更多计算，其单位内存收益会更高。

4.2 Attention 的计算收益

FAttn(n) = NAttn × [FAttn(Ltotal) − FAttn(Lparent)]

这里不是只算 20 个 token 的局部 Attention。Attention 的计算成本与上下文长度有关，新增 token 还要与前面的上下文交互，所以代码用“完整前缀的估算 FLOPs − 父路径前缀的估算 FLOPs”来估算增量。

举例：如果处理 100-token 前缀的 Attention 估算为 1.0 单位，处理 120-token 前缀估算为 1.5 单位，那么当前节点对应的增量是 1.5 − 1.0 = 0.5 单位，而不是 1.5 单位。

4.3 MLP 的计算收益

预期形式：FMLP(n) = NMLP × [FMLP(Ltotal) − FMLP(Lparent)]

MLP/FFN 通常按 token 逐个进行投影与非线性计算，因此增量收益可理解为新增 token 对应的 MLP 计算量。若每个 token 的 MLP 计算量近似固定，新增 20 个 token 就大致对应 20 个 token 的 MLP 计算。

源码审查提醒：当前仓库 radix_cache_hybrid.py 的 evict_v2() 中，MLP savings 的减项写成了 get_attn_flops(seqlen_parent, ...)，而不是预期的 get_mlp_flops(seqlen_parent, ...)。因此，理解算法时应使用上面的“MLP 总量差分”作为概念模型，同时把实际实现中的这行视为值得核查的疑似笔误/实现问题，不能默默把它当作正确公式。

4.4 把不同层的收益相加

Fsaved(n) = FSSM(n) + FAttn(n) + FMLP(n)

三个部分分别估算缓存命中后能避免的 SSM、Attention 和 MLP 计算，然后求和。注意它是模型计算量的估算指标，不等于真实墙钟时间；GPU kernel、带宽、并行度、批处理等都会影响实际延迟。

5. 内存成本：保留它要占多少字节？

计算收益回答“能少算多少”；内存成本回答“为这份收益要一直占用多少缓存空间”。源码将候选节点的内存估算为 SSM 状态内存加 KV 内存：

M(n) = NSSM × MSSM-state + NAttn × MKV(Ltotal)
  • N_SSM × M_SSM-state：所有 SSM 层的状态总量。对于固定模型配置，通常与该节点之前累计的 token 数没有线性关系。
  • N_Attn × M_KV(L_total)：Attention 层的 KV 缓存量，通常随完整前缀长度增长。
  • L_total 是从根到节点的完整前缀长度，而非仅当前节点的 token 数；这反映了该缓存检查点所代表的前缀状态。

假设某节点的 SSM 状态合计 8 MB，KV 缓存合计 12 MB，则：

M(n) = 8 MB + 12 MB = 20 MB

这里的数字仅为解释用的假设值，并非论文实验数据或某个特定模型的实测结果。

重要直觉：KV 通常随序列长度增长；SSM 状态的存储大小对固定模型配置通常较固定。于是长前缀的 SSM 状态可能用相近的内存，避免掉更多前缀计算；这正是只看“最近访问时间”不够的原因之一。

6. 计算效率：收益除以内存

E(n) = Fsaved(n) / M(n)

这个值可以读成：每占用一个字节（或同一单位的内存），缓存命中时能避免多少 FLOPs。 分子越大越好，分母越小越好，因此比值越高，内存使用效率越高。

用数字走一遍

下面是假设的三个候选节点。为便于理解，计算收益使用“百万 FLOPs”的抽象单位，内存用 MB；数字仅用于演示。

节点计算收益内存成本效率 = 收益/内存解释
A：短前缀10010 MB10绝对收益不高，但很省内存。
B：长前缀60030 MB20占用较多内存，但每 MB 节省的计算最多。
C：内存大、收益一般18030 MB6单位内存换来的计算收益最少。
节点 A100 ÷ 10 = 10中等效率
节点 B600 ÷ 30 = 20最高效率
节点 C180 ÷ 30 = 6最低效率

如果只看绝对计算收益，C 的收益 180 大于 A 的 100，似乎 C 更有价值；但按内存归一化后，A 每 MB 节省 10 单位计算，C 每 MB 只节省 6 单位。内存有限时，C 更可能成为低效率候选。

但这还不是最终决定。Marconi 还会考虑最近访问程度：即使某节点效率很高，如果长期没有访问，也可能被驱逐；反之，最近刚命中的节点即使效率一般，也可能暂时留下。

7. 最终打分与选谁驱逐

Marconi 将计算效率与最近访问程度合成一个 utility score。论文中的表达式为：

S(n) = recency(n) + α × flop_efficiency(n)

其中 recency 与 flop efficiency 都归一化到相同范围，避免单位不同的量直接相加；α 控制计算效率的权重。分数越高，越值得保留；分数最低的候选节点优先驱逐。

分数由两部分构成

Recency：最近是否访问

原始信号 ≈ 1 / (当前时间 − 最后访问时间)

刚访问过的节点，时间差小，倒数大，归一化后通常得到更高的 recency 分数。

FLOP efficiency：单位内存收益

原始效率 = FLOPs saved / bytes

能用较少内存节省大量计算的节点，效率分数更高，更有保留价值。

打分例子

假设归一化后，节点 A 的 recency = 0.9、效率 = 0.2；节点 B 的 recency = 0.2、效率 = 0.9。为演示，令 α = 1：

节点Recency效率总分 S结果
A：刚访问但效率低0.90.21.1更值得保留
B：较久未访问但效率高0.20.91.1同分，实际结果取决于具体数值和并列处理

如果 B 的效率进一步提高，或 A 的 recency 降低，B 的总分就可能更高。这个例子说明算法不是单独按某一个指标排序，而是在两者之间做权衡。

α 的含义：α 越大，算法越重视计算效率；α 越小，越重视最近访问程度。α = 0 时，公式退化为只看 recency 的策略（在其他实现细节相同的前提下）。论文/实验代码还涉及通过工作负载调节 α；不要把示例中的 α = 1 当成仓库固定默认值。

一次驱逐迭代

  1. 收集所有叶子和单子节点。
  2. 对每个候选计算预计 FLOPs 节省量。
  3. 估算该节点对应的 SSM 状态和 KV 内存。
  4. 算出 FLOPs/byte，分别归一化效率和 recency。
  5. 用 recency + α × efficiency 计算 utility。
  6. 挑最低分候选：叶子直接删除；单子节点则释放自身 SSM 状态并与子节点合并。
  7. 累计释放的内存还不够时，重新收集候选并继续。

8. α 的自适应选择：启动采样 → 回放搜索 → 应用最优权重

前面只讲了 S(n) = normalized_recency(n) + α × normalized_efficiency(n)，但真实工作负载随时间变化，最佳 α 不是先验常数。Marconi 用启动期真实请求来调权。

启动：α = 0，按 LRU 驱逐
↓
第一次驱逐：记录此前请求数 R，并保存 radix tree 快照
↓
Bootstrap：继续用 LRU，并记录请求的 token 级信息
↓
达到采样窗口后，并行回放同一批请求，测试不同 α
↓
更新 α，继续在线服务

窗口和搜索的具体设置

环节论文描述GitHub 当前实现的对应项
初值首次驱逐前 α = 0，先按 LRU 运行eff_weight=0
采样窗口首次驱逐前请求数的 5–15 倍bootstrap_multiplier=5（仓库默认；窗口长度为 5 × R，并非运行时自动在 5–15 倍间选择）

一个可复现的计算例子

假定第一次驱逐前共有 R = 100 次请求。按仓库默认值，接下来收集 500 次请求作为 bootstrap 样本；用相同的树快照和这 500 次请求，分别模拟 α = 0、0.1、…、2.0 对缓存替换的影响，再按设定的目标函数比较。这样比较的是同一批工作负载下的反事实结果，不是在生产路径上把 21 种 α 各运行一遍。

# 对应实现逻辑的简化伪代码（不是逐字源码）
alpha = 0
R = requests_seen_before_first_eviction
bootstrap_window = 5 * R  # 仓库默认值
snapshot = clone(radix_tree_at_first_eviction)
trace = collect_next_requests(bootstrap_window)
results = parallel_replay(snapshot, trace,
                          alphas=[0.0, 0.1, ..., 2.0])
alpha = argmax(results, key=total_flops_savings)  # 公开代码

为什么不是固定取一个大 α？不同工作负载的前缀重用频率、路径长度和状态大小分布不同：有的适合偏向“最近命中”，有的适合偏向“每字节能够省下更多 FLOPs”。这相当于用少量启动样本为驱逐策略做一次 workload-specific 校准。

8A. 从零手算一次调参回放：5 个请求、2 个 α、每一步都能核对

先记住一句话：回放时模型不跑 GPU，只模拟“查找前缀 → 命中统计 → 插入缓存 → 内存不足时驱逐”。两个 α 使用同一个初始快照、同一批按顺序到来的请求和相同容量。不同 α 只会通过“驱逐哪个节点”影响未来能命中的前缀。

Step 0：把实验条件写清楚

构造一个故意很小的玩具模型（并非论文真实模型），方便整数手算：D = 4、N = 2，Attention = 1 层、SSM = 1 层、MLP = 1 层；按源码默认 expand = 2、conv_kernel = 4，所有状态元素各占 2 bytes。

先令每条无共享前缀的独立缓存路径视为一个可淘汰的“条目”（这是教学抽象；真实 Marconi 会管理压缩树节点和不同类型的状态）。缓存总容量为 320 bytes。三段前缀如下，互不共享 token：

名称token IDs长度缓存字节数（如下计算）
P[11,12]2144 bytes
Q[21,22,23,24]4176 bytes
R[31,32]2144 bytes

为什么是 144 和 176？注意 MLP 虽然贡献 FLOPs，但不存历史 KV/SSM 缓存：

SSM 状态 = 2DN + 2(eD + 2N)k = 2×4×2 + 2×(2×4+2×2)×4 = 112 bytes
Attention KV = 4LD = 16L bytes；所以 M(2)=112+32=144，M(4)=112+64=176。

按时间顺序收到五个请求；为专注回放机制，假定输出为空（因此插入的是输入 token 序列），且启动时的模拟缓存为空：

时刻请求输入 token 数说明
t1P2首次出现 P
t2Q4首次出现 Q
t3P2再访问 P，让 P 比 Q 更新近
t4R2触发容量不足，α 开始发挥作用
t5Q4检验 Q 在 t4 后是否仍被保留

Step 1～3：所有候选策略的缓存都相同

时刻查前缀（回放时不执行模型）操作后缓存已占空间
t1：P未命中，h₁=0；插入 P{P}144
t2：Q未命中，h₂=0；插入 Q{P,Q}144+176=320
t3：P命中 P 的全部 2 token，h₃=2；刷新 P 时间戳{P,Q}320

Step 4：R 到来，容量不够，模拟两种 α

要插入 R（144 bytes），而已有 P+Q 占用 320 bytes，必须先淘汰至少一个条目。此时 P 最近访问、Q 较久之前访问；假设根据候选集合做 min-max 归一化后恰好得到：

候选访问新近程度 R(n)节省 FLOPs / byte 归一化 E(n)
P（最近用过，但效率低）10
Q（更旧，但效率高）01

此处 R、E 的归一化值为特意构造的教学数据，用来展示 α 的作用；不声称它们恰好由上面玩具模型的真实节点评分算出。实际代码按具体节点 FLOPs 效率、时间戳以及候选集合归一化。

score(P)=1+α×0=1；score(Q)=0+α×1=α。分数低的先驱逐。
α = 0（纯近期性）

score(P)=1，score(Q)=0 → 驱逐 Q，腾出 176 bytes，插入 R。

t4 后缓存 = {P,R}，占用 288 bytes。

α = 2（效率权重更高）

t4 后缓存 = {Q,R}，占用 320 bytes。

这就是整个网格搜索为什么有意义的唯一关键：同一请求序列，缓存状态从 t4 起发生了分叉。

α=0 的副本

9A. 从最基础的矩阵乘法推导：8LD² 究竟是哪来的？

建议学习顺序：先搞懂 ①“一个乘加为何约算 2 FLOPs”；②“矩阵的形状为何产生 LD²”；③“Q/K/V/O 四次投影为何产生系数 8”。这里不需要预先懂 CUDA。

① FLOPs 是什么？为什么矩阵乘法有一个系数 2？

FLOP 表示一次浮点操作。计算单个向量点积 y = a₁b₁ + a₂b₂ + … + aₖbₖ，有 k 次乘法和约 k 次加法，估算为 2k FLOPs（严格计数为 k 次乘法与 k−1 次加法；这里沿论文惯用近似）。

如果 A 的形状为 [m,k]，B 为 [k,n]，则输出 C=A×B 的形状为 [m,n]，一共有 m×n 个输出元素，每个需要约 2k FLOPs：

FLOPs(matmul) ≈ 2 × m × n × k

② 为什么 Linear 层会有 LD²？

假设一次处理 L 个 token，每个 token 的隐藏向量有 D 个浮点数。堆叠后的输入 X 的形状就是 [L,D]。一个保持维度不变的线性层使用权重 W:[D,D]，输出 Y=XW:[L,D]：

X [L,D]  ×  W [D,D]  →  Y [L,D]
                ↑              ↑
         每个输出点积 D 项     共有 L×D 个输出
FLOPs = (L×D) × (约 2D) = 2LD²
这里 L 代表批量中的序列长度，D² 不是把 token 数平方，而是权重矩阵有 D×D 的输入输出连接。系数 2 来自乘法和加法都计入 FLOPs。

③ Attention 的 8LD²：Q、K、V 和 Output 共四个 Linear

以源码使用的简化全维度注意力模型为例，Q、K、V、输出投影，每个都按 [L,D] × [D,D] 计算：

操作矩阵形状FLOPs
Q = XWq[L,D] × [D,D]2LD²
K = XWk相同2LD²
V = XWv相同2LD²
O = AttentionResult·Wo[L,D] × [D,D]2LD²
四个 Linear 合计8LD²

然后是 Attention 自身的两次矩阵乘法（所有注意力头的维度加起来为 D）：

Q [L,D] × Kᵀ [D,L] → Scores [L,L]   : 2L²D
Prob [L,L] × V [L,D] → Context [L,D]: 2L²D
合计                                    : 4L²D
F_attention(L) ≈ 8LD² + 4L²D

softmax、归一化等操作在这里被省略或视作低阶项。此式是 Marconi utils.py 第 17–41 行 采用的成本模型；GQA/MQA/MLA 或具体架构不一定满足四个等大的 D×D 投影。

④ MLP 的 16LD²：先扩张到 4D，再收缩到 D

第一层: [L,D] × [D,4D] → [L,4D]  : 2 × L × D × 4D = 8LD²
激活函数: [L,4D]                 : 低阶项，公式忽略
第二层: [L,4D] × [4D,D] → [L,D] : 2 × L × 4D × D = 8LD²
合计                            : 16LD²

MLP 的激活函数（如 GELU/SiLU）让两层 Linear 的组合成为非线性变换。源码中的 16LD² 是两层、扩张 4 倍的简化模型；不能不经修正直接套在每个 SwiGLU/MoE 结构上。源码：get_mlp_flops()。

⑤ 用小数字实际计算一次

设 L=3、D=4，一次 D→D Linear 有 2×3×4×4=96 FLOPs；Q/K/V/O 四个 Linear 就是 4×96=384；注意力乘法两项为 4×3²×4=144，总计 528 FLOPs。而 MLP 为 16×3×4²=768 FLOPs。因此这些系数是具体矩阵形状计算出来的，而非经验常数。

⑥ SSM 的 12LD² + 16LDN + 10LD 如何理解？

12LD² 源于 Mamba 内部若干个以 D 或 2D 为主要宽度的投影；16LDN 是与宽度 D、递归状态维度 N 同时相关的投影、门控与 scan 等操作；10LD 是逐元素/卷积等操作的聚合近似。各项的具体推导需结合 Mamba1 架构和 expand=2 的假设，不是每一个常数都由单个 Linear 产生。

# 公开源码给出的分组（非逐个 kernel 的性能测量）
# utils.py: get_mamba1_flops(l,d,n)
matmul_terms = 12 * L * D**2
vector_terms = 16 * L * D * N
scalar_terms = 10 * L * D
F_ssm = matmul_terms + vector_terms + scalar_terms

源码注释逐项列出 input projection、1D conv、dt projection、scan、output 等，且说明最初版本末项误写为 10L，camera-ready 改为 10LD。详见 utils.py 第 61–98 行。

9B. Linear 的“状态”到底是什么？区分参数、激活、KV Cache 和 SSM State

先说结论：普通 Linear 层并没有需要跨请求保存的“递归 State”。 你可能混淆了模型权重、每层计算得到的 hidden state（激活）和用于后续增量推理的缓存状态。

对象示例、形状什么时候保存？是否计入 Marconi 的前缀缓存？
模型参数（权重）Linear 的 Wq:[D,D]、W1:[D,4D]模型加载时存入显存；不同请求共享否；它是模型本体，不是每条请求的历史
hidden state / 激活第 ℓ 层 token t 的 xt(ℓ) ∈ RD前向计算时产生，送往下一算子/层；不意味着永久保留一般否；计算图中临时张量另算
Attention KV Cache历史 token 的 K、V；每层随 token 增长生成后续 token 时要用是
SSM 递归状态处理到 t 时的 ht，随 token 更新计算下一个 token 要用；也可在前缀边界存检查点是
Conv1D 历史窗口最近若干 token 的中间特征递归/流式卷积使用是（Marconi 的 Mamba 状态成本包含它）

把一个普通 Linear 写成 y_t = W x_t + b：W 是模型参数，x_t/y_t 是本次 token 的激活；下个 token 不需要先读取 Linear 的某个可更新内部状态。与之相反，SSM 的简化递归为：

ht = Atht−1 + Btxt；   yt = Ctht

这个 h_t 才是随着输入序列不断更新、下一 token 必须依赖的 State。若某个前缀是 [A,B,C]，保留下处理完 C 的 h3，就可以从 D 继续推进；但若要在 B 分叉产生另一条请求，仅有 h3 通常无法逆推出 h2，因此要在 B 处另存检查点，或从更早的检查点重新计算。

共同前缀 [A,B]：SSM 检查点 h₂；KV(A,B)
↙　　　　　　　　　↘
请求 1 继续 C：h₃；KV(C)
请求 2 继续 D：h'₃；KV(D)

而 MLP 虽然在命中前缀后也可以跳过重算，但不是因为缓存了各个 MLP 的 hidden state，而是因为这个前缀对应的 KV 和 SSM 状态已经足够让后续增量计算从正确位置继续。因此 F_mlp 计入“节省的计算”，MLP 不单独计入“历史状态缓存字节”。

9C. 从 Marconi 源码追踪内存：逻辑节点、状态对象、字节数、物理位置

先划定证据边界：公开 artifact 的 radix_cache_hybrid.py 实现的是Radix Tree 缓存策略/容量模拟；未展示 KV page table、CUDA allocator、GPU block pool 或显存地址映射。论文谈到的 Jenga 物理分配器设计与这份可运行 Python artifact 的实际实现层次必须分开看；不能根据 capacity_bytes 推断已分配物理显存。

① 逻辑索引：前缀 token 决定找哪一个 TreeNode

② KV 与 SSM 的不同粒度：一个按 token 增长，一个按检查点计数

KV：节点边上的 token

父节点 [A,B]，子节点边 [C,D]，子节点的 KV 成本按 2 个 token 计算。树中不重复把父节点 [A,B] 的 KV 加入每个子节点边的 token 计数。

KV_bytes = A_layers × get_kvs_size(2,D)
SSM：节点边界检查点

每个非根节点按一份跨所有 SSM 层的边界状态计数，而不是节点里每个 token 都保存一个 SSM state。

SSM_bytes = S_layers × get_mamba_state_size(D,N)

直接证据：第 424–434 行的 _get_num_cached_tokens_helper()，每个非根节点为 total_num_cached_mamba_states = 1、total_num_cached_kv_tokens = len(node.value)。随后 第 170–181 行按两个计数分别乘单元成本。

③ 内存总账：完全由大小模型计算

# get_state_size() 简化摘录

④ 用论文默认 7B 参数算一次真实的“理论容量账”

取 D=4096、N=128、SSM 层数 24、Attention 层数 4、FP16。每个 Attention 层单 token KV = 2(K/V) × 4096 × 2 bytes = 16,384 bytes = 16 KiB；4 层一共 65,536 bytes = 64 KiB/token。

每个 SSM 层的边界状态为 4096×128×2 + (2×4096+2×128)×4×2 = 1,116,160 bytes；24 层共 26,787,840 bytes ≈ 25.55 MiB/检查点。

9. 附录公式：究竟如何估算 FLOPs 和占用字节？

先统一符号：L = token 序列长度；D = 模型隐藏维度；N = SSM 状态维度；A、S、P 分别为 Attention、SSM/Mamba 和 MLP 层数。下列 FLOPs 是论文/实现采用的近似前向计算模型，并不是所有模型架构的通用精确计数。

单层 FLOPs：长度为 L 的前缀

组件一次处理 L 个 token 的 FLOPs直观解释
AttentionF_attn(L) = 8LD² + 4L²D线性投影贡献 O(LD²)，全注意力矩阵贡献 O(L²D)

状态内存：论文简化口径与源码实际口径

组件缓存状态大小（字节）假设 / 补充
单层 Attention KVM_KV(L) = 2 × L × D × 2 = 4LDK 和 V 各一份，元素按 FP16 的 2 字节计；这里用论文的简化维度设定
单层 SSM 核心状态M_SSM,core = 2DNSSM 状态元素按 2 字节计；不随 L 增长
单层 SSM 完整状态M_SSM,full = 2DN + 2( eD + 2N )k加上 Conv1D 状态；e 为 expand 倍数、k 为卷积核宽。源码默认 e=2、k=4
整模型缓存开销（示意）M_total(L) = A × 4LD + S × M_SSM,full按各层的类型相加；无状态的 MLP 本身不增加 KV/SSM cache
为何公式里 Attention 有 L²，而 KV 只有 L？ 完整前缀的注意力计算需要 token 两两交互；但已算完的每个 token 只需存对应 K/V。SSM 计算随前缀长度增长，但其最终递归状态大小（忽略卷积参数配置变化）不随历史长度增长。

从 FLOPs / byte 推出表格里的效率

Attention: F_attn(L) / M_KV(L) = (8LD² + 4L²D) / (4LD) = 2D + L
SSM 核心状态口径: F_ssm(L) / M_SSM,core = L × (6D/N + 8 + 5/N)

SSM 比值采用上面已修正的源码末项 10LD，若按论文早期出现的 10L 末项，最后一项会写成 5/(DN)；两种写法的差别来自 FLOPs 公式版本，且不应与纳入卷积状态后的实际分母混淆。

把论文的 7B 混合模型参数代进去

以论文举例的 D = 4096、N = 128、S = 24 层 SSM、A = 4 层 Attention、P = 28 层 MLP 为例：

单层 Attention 理论效率L + 8192 FLOPs/byte随 L 线性增加
单层 SSM 核心状态理论效率约 200.04 × L FLOPs/byte不计 Conv1D 状态时

这说明在该理论成本模型中，越长的序列对应越高的 SSM 状态复用收益；但不能直接拿“200L”作为任意树节点的最终淘汰分数，还必须考虑节点相对于父路径新增长度、每层分工、已有父前缀及归一化。

从“单层理论效率”到“某个节点的候选效率”

设某个节点自己的边上有 ΔL 个 token，从根到该节点总共有 L 个 token，父节点路径长度为 L₀ = L − ΔL。节点级收益不能一律把完整 L 的 FLOPs 当成“节点独有”：

# 按论文建模逻辑组织的节点级收益（修正为一致的 MLP 差分）
F_saved(node) = S * F_ssm(ΔL)
              + A * [F_attn(L) - F_attn(L₀)]
              + P * [F_mlp(L)  - F_mlp(L₀)]

M_node_proxy = S * M_SSM,full + A * M_KV(L)
E_node = F_saved(node) / M_node_proxy

其中 M_node_proxy 表示源码为候选打分采用的状态成本代理，不应机械理解为“驱逐这个内部节点，真实一定释放这么多新字节”。释放字节的数量要结合叶子删除或单子节点合并的具体路径判断。

源码勘误：radix_cache_hybrid.py 的可见实现中，flops_savings_mlp 的减项写成了 get_attn_flops(L₀, D) 而不是预期的 get_mlp_flops(L₀, D)。上面展示的是数学上一致的差分，不代表源码原样如此执行。

10. 命中叶子后，父节点引用数会增加吗？

要区分“被访问”“访问时间戳更新”“引用计数增加”这三件事。它们不是同一个操作。

Marconi 代码的匹配逻辑

match_prefix() 通过树遍历找到最长可匹配前缀，并记录匹配路径上访问到的节点。V2 的时间戳更新重点在最深的匹配节点，而不是像传统树 LRU 那样把所有祖先都更新为刚访问过。

# 概念性示意
nodes_accessed.append(child)
...
nodes_accessed[-1].last_access_time = self.logical_ts

因此，如果匹配到叶子 C，C 的时间戳会更新；不能据此推断父节点 B 的时间戳也更新，更不能推断 B 的引用计数会增加。

结论：在这份 Marconi 研究实现里，所讨论的 TreeNode 路径没有通过 ref_count/lock_count 来完成上述驱逐策略的核心判断。匹配到叶子并不意味着父节点引用计数自动加一。

生产推理引擎可能另外实现 pin/unpin、引用计数或锁，防止正在被请求使用的 KV 块被释放。但这是运行时并发和内存安全机制，必须检查具体引擎代码，不能仅凭 Marconi 的树缓存逻辑推导出来。

为什么父节点时间戳不更新仍然合理？

Marconi 的策略会把祖先 KV 视作可以由更深节点的缓存路径覆盖的内容；同时，祖先 SSM 状态本身并不是命中更深节点时必然需要单独复用的检查点。因此，如果每次命中叶子都把所有祖先标成“刚用过”，就会让一些低价值的中间检查点长期显得很热，妨碍释放其 SSM 状态。

11. 源码阅读时的注意点

公式说明的是策略意图，代码决定了实际行为。阅读 radix_cache_hybrid.py 的 evict_v2() 时，至少要核查以下细节：

  1. MLP 差分公式：当前可见实现中，flops_savings_mlp 的父路径减项调用了 get_attn_flops(seqlen_parent, ...)，而非 get_mlp_flops(seqlen_parent, ...)。这与常规的 MLP 差分公式不一致，可能是实现错误。
  2. 叶子释放内存的变量：同一函数中，叶子分支累计释放字节的表达式出现 len(node.value)，而真正选中的变量是 node_to_evict。需要检查该作用域中的 node 是否就是当前候选；若不是，可能导致内存释放量统计错误。
  3. 估算值不等于实测延迟：FLOPs/byte 是策略的代理指标，不直接等价于毫秒数，也未完整刻画 GPU 带宽、kernel 启动、批处理和并发影响。
  4. 候选不等于必删：节点满足“叶子或单子节点”只是进入候选集；是否被驱逐还要看 utility score 和当下需要释放的内存量。
  5. 论文与仓库版本可能有差异：论文公式用于理解设计，实际代码应以你检查的 commit 为准。读代码时最好记录仓库 commit hash，避免之后主分支变化导致行号或实现不同。

12. 完整流程总结

请求匹配前缀
↓
记录最深匹配节点的访问时间
↓
收集叶子 + 单子节点候选
↓
计算每个节点可避免的 SSM / Attention / MLP FLOPs
↓
估算 SSM 状态 + KV 的内存成本
↓
效率 = 计算收益 / 内存成本
↓
归一化 Recency 与效率，计算 utility
↓
驱逐最低分候选
叶子：直接删除
单子节点：释放自身 SSM，合并路径
一句话记忆：Marconi 在可安全处理的候选节点中，权衡“最近有没有用过”和“每单位缓存内存能避免多少计算”；它不只追求命中次数，还希望把有限的内存留给更有计算价值的前缀状态。
